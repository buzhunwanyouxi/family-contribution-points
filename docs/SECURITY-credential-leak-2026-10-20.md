# 凭据泄漏:根因、处置、以及为什么这类事会重复

> **本文件记录 2026-10-20 的一起真实事故,以及为它加的机制。**
> 记录它的理由不是自我批评,是**让别人不用再踩一次**。

---

## 一、发生了什么

| 时间 | 事件 |
|---|---|
| 2026-10-20 19:41 | 在 Edge 里打开 `localhost:5173`(前端 dev server),登录页出现 |
| 19:41 | Edge **自动填充**把两个值填进表单:`#account` = `https://api.deepseek.com`,`#password` = 一个真实 API Key |
| 19:41 | 我用 `browser_a11y` 读页面结构,**读数里包含输入框的当前值**,于是 key 进入了对话 |
| 19:41 | 我清空了输入框,**没有提交**到任何接口 |
| 23:30 | 我把这件事写进 ops 日志,并把 key 的**明文**当"证据"抄了进去 |
| 23:30 | 提交 `b78ac3e` 推送到 `main`。**仓库是公开的** |
| 次日 | 发现并遮蔽。此时 key 已公开约 12 小时 |

---

## 二、两个独立的原因,任何一个单独存在都不会出事

### 原因 A:Edge 里存了一条完整的"密码记录"

实测(读 `Edge\User Data\Default\Login Data`):

```
origin   = http://localhost:5173/      ← 本项目的 Vite dev server 端口
username = https://api.deepseek.com
password = (66 字符,加密存储)= 那个 key
times_used = 5                          ← 已经被自动填了 5 次
```

还有第二条:`http://127.0.0.1:5199/`,同样的账号密码对,`used=0`。

**为什么会被保存**:某个时刻,有人在 `localhost:5173` 的某个**两栏表单**里
(把 `https://api.deepseek.com` 填进"账号"、把 key 填进"密码")提交过,
Edge 弹出"是否保存密码"并被确认了。

**这是自动填充的正常行为,不是漏洞。** Edge 认为那是一个登录表单,就记住了。

**但后果很糟**:任何跑在 `localhost:5173` 的页面 —— 包括本项目的登录页 ——
打开就会被填上这对值。而**登录页的"密码"框和"API Key"框长得一样**。

### 原因 B:我把读到的值当"证据"写进了公开文档

`browser_a11y` 会返回输入框的**当前值**。这是它的功能,不是缺陷 ——
没有它就不知道表单填没填对。但同一件事的另一面是:

> **任何被自动填充进表单的密钥,对 Agent 都是明文可见的。**

而我当时的判断是"这是个安全隐患,记下来给使用者看"。**记的方式错了**:
我把值抄进了会公开的文档。正确的写法是只写形状(`sk-…`、长度、来源),不写值。

## 三、处置

| # | 动作 | 谁做 | 状态 |
|---|---|---|---|
| 1 | **吊销那个 API Key 并重建** | **所有者** | ⬜ **必须做,这是唯一真正的修复** |
| 2 | 遮蔽仓库里的明文 | 已完成 | ✅ |
| 3 | 删除 Edge 里 `localhost:5173` 的密码记录 | 所有者 | ⬜ 见下面"怎么删" |
| 4 | 删除 Edge 自动填充里的 `apiKey` 条目 | 所有者 | ⬜ |
| 5 | 加机器检查(`pnpm check:secrets`)并接入 CI | 已完成 | ✅ |
| 6 | 重写 git 历史去掉 `b78ac3e` 里的明文 | 待定 | ⬜ 见第 5 节 |

> **顺序很重要**:先吊销,再清理。
> 反过来没有意义 —— 遮蔽一个仍然有效的密钥,只是让它更难被发现。

## 四、怎么删 Edge 里的那条记录(只有所有者能做)

1. 地址栏输入 `edge://settings/passwords`
2. 找到 `localhost:5173` 那一条(用户名是 `https://api.deepseek.com`)
3. 删除它。**顺带检查 `127.0.0.1:5199` 那条,一并删掉**
4. 再打开 `edge://settings/personalinfo`(自动填充)→ "表单信息" → 删除含 `apiKey` 的条目

**删完可以这样验证**(不依赖 Edge 的界面):

```powershell
# 先完全退出 Edge,再跑;Edge 运行时数据库是锁的,读到的是旧副本
```

> ⚠️ **本项目没有自动化这一步。** 理由:在 Edge 运行时改 `Login Data` 有损坏全部已存密码的风险,
> 而"丢失所有网站密码"比"多留一条记录"严重得多。**这件事必须人工做。**

## 五、为什么不自动重写 git 历史

`b78ac3e` 里含明文,重写历史能把它从 `main` 上抹掉。**但代价明确**:

| 好处 | 代价 |
|---|---|
| 公开仓库不再显示明文 | 所有已克隆的人(包括 `sun-521-s`、`MIAO98J`)必须重新克隆或强制对齐 |
| 强推后 GitHub 的缓存可能仍保留一段时间 | 提交 sha 全变,`INDEX.md`、ops 日志里的引用全部失效 |

**而且重写历史并不能让已泄漏的密钥变安全** —— 它已经被抓取/缓存过了。
**所以:吊销是必需的,重写是可选的。**

**当前决定**:先不重写。等 `sun-521-s` / `MIAO98J` 有活动迹象时再做,避免单方面打断他们的本地仓库。

## 六、加上的机制:`scripts/check-secrets.mjs`

```
pnpm check:secrets
```

- 扫描**被 git 跟踪的文件**(未跟踪的不算:不会进仓库,报了只是噪音)
- 5 类规则:`sk-`(OpenAI/DeepSeek)· `ghp_` 等 GitHub · `AKIA`(AWS)· `xox`(Slack)· `sk-ant-`(Anthropic)
- **只报文件:行号 + 前缀**(`sk-abcde…(35 字符)`),**不回显完整值** ——
  否则报告本身就成了新的泄漏源
- 每条规则的报错里带**去哪吊销**的链接
- 接入 `.github/workflows/ci.yml`,每次推送都跑

**明确它做不到什么**:
- 不查 git 历史(查了也没用,历史只能靠吊销)
- 不做熵检测(中文文档里长随机串太多,会淹没在假阳性里)
- **它拦不住"我把值写进**未跟踪**的文件再手动 `git add -f`"** —— 这类只能靠人

## 七、通用教训(与本项目其他事故同构)

> **1. 两个独立的疏忽同时出现才会出事。**
> 自动填充填了 key(正常行为)+ 我把值抄进公开文档(我的判断失误)= 泄漏。
> 任何一个单独存在都不会有问题 —— 所以"只修一个"看起来会像修好了。
>
> **2. "记录下来给别人看"和"记录内容"是两件事。**
> 我本可以写"有一个 sk- 开头的密钥被自动填进了密码框(长度 35)",信息量一样,风险为零。
>
> **3. 公开仓库的默认假设应该是:写进去的东西会被人看到。**
> 这不是悲观,是这个仓库的用途 —— 它就是为了给别人读才公开的。
