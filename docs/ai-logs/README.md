# 日志与报告书写规范(所有协作者必读)

本项目由 **3-6 名开发者 + 各自的 AI 助手**并行开发。为了让每一轮工作都能被后来者读懂,每轮工作必须留下**两份**文件:

| 目录 | 面向谁 | 风格 | 必须回答的问题 |
|---|---|---|---|
| `ops/` | **其他 AI** | 结构化、可机器扫描、只讲事实 | 改了什么文件?接口/表怎么变?留了什么坑?怎么验证? |
| `reports/` | **人类操作者** | 人话、有结论、不超过一屏 | 做了什么?我怎么亲手验证?有什么风险?要我决策什么? |

**两份都必须写。** 没做完、卡住了,同样要写 —— 说明卡在哪,能救下一个人半天时间。

## 四、十二条书写纪律

1. **只追加,不改写。** 不许修改或删除别人的日志。写错了就在自己新日志里加"更正说明:原文件 X 的 Y 说错了,实际是 Z"。
2. **文件名带时间戳**,避免重名冲突。
3. **变更文件清单必须完整**。日志说 3 个文件、PR 里 8 个文件 = 审查直接打回。
4. **破坏性变更必须在第 3 节标红加粗**,并在此处 @ 受影响的模块负责人。
5. **不写感想、不写感谢、不写"我觉得很棒"**。ops 日志是给机器和同行看的。
6. **report 不超过一屏**,超过就说明你写成了 ops。
7. **每份日志写完,去 `INDEX.md` 追加一行**,否则等于没写。
8. **同步更新 `OWNERS.md`**:开工时标"进行中",完成时标"已完成"(填完成日期)。
9. **验证命令必须可直接复制执行**,不要写"自己起服务试一下"。
10. **卡住时也要写**:写清楚阻塞点、你已经试过什么、你判断需要谁介入。
11. **★ 第 7 节(交接建议)必填**。哪怕你只改了 3 行,也要写"下一个人该先读什么、别踩什么"。
    这一节的存在理由:**别人读你的代码要花 10 分钟,读你的 3 行建议只要 10 秒**。
12. **★ 第 8 节(别人代码的问题)必填,没有就写"无"**。发现别人的问题**只写不改**,
    并带上证据(命令输出 / 文件行号 / 官方文档链接)。写"无"是一个明确结论,空着不算。

> **为什么第 11、12 条是强制的**:本项目是 3 人 + 3 个 AI 并行开发,信息不对称是最大的成本。
> 实测教训:两位协作者各自按冻结契约一次做对,但**两人的 PR 同时合并时,在 4 个共享文件上产生了冲突**
> (路由注册、契约表、日志索引、模块认领表)—— 见 `docs/ai-logs/ops/2026-10-12-*`。
> 冲突不是能力问题,是**并行开发的必然结果**;而能把它从"两小时解冲突"压缩到"十分钟看懂"的,
> 正是这两节:交接建议让接手者不迷路,问题清单让问题在合并前就被发现。
