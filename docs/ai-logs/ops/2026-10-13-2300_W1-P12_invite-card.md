## 5. 阻塞与风险(需要谁配合)

### ★ 发现 1(严重):token 从来没被持久化,前端**从未真正连通过后端**

**现象**:`VITE_USE_MOCK=false` 时,注册"成功"→ 立刻跳回登录页。

**定位过程**(服务端日志是关键证据):

```
req-2  POST /api/auth/register  → 201     ← 注册成功
req-3  POST /api/families       → 401     ← 紧接着就 401
```

**根因**:`apps/web/src/app/session.tsx` 的 `applyAuth` 只把 `user` / `families` 写进 React state,
**从未调用 `setToken(...)`**。于是:

- 会话在内存里"看起来是登录的"(页面显示"爸爸,你可以创建…")
- 但任何带鉴权的请求都没有 `Authorization` 头 → 401 → 客户端清 token 并登出

**为什么一直没被发现**:

1. **mock 模式不走 token** —— `api/mock.ts` 从不检查鉴权,所以开发时一切正常;
2. **`setToken` 的导入"用过了"** —— `clear()` 里调用了 `setToken(null)`,所以 `tsc` 与将来的 lint
   都不会报"未使用";
3. **没有任何测试覆盖"前端 × 真实后端"** —— 后端的 226 个测试全在自己内部造数据。

**结论:这个 bug 意味着在它修好之前,前端从来没有真正跑通过真实后端。** 它只在
`VITE_USE_MOCK=false` 时才暴露,而这正是"上线"的配置。

**修法**:`applyAuth` 接受可选 `token` 并**先写 token 再写 state**(顺序重要:先持久化,
避免中途返回导致内存态与存储态不一致)。`refresh()` 走 `api.me()`(无 token 字段)时行为不变。

**防复发**:
- `api/config.ts` 顶部写明"**mock 模式无法发现鉴权 bug**,宣称完成前必须用真实后端跑一次";
- 本轮把真实浏览器链路作为**验收证据**(见第 6 节)。

### ★ 发现 2:前端没有任何测试,而 web 的 `test` 脚本是个空壳

`apps/web/package.json` 里 `"test": "echo \"(todo) vitest\""`,且缺少 `jsdom` /
`@testing-library/react`。本轮**没有为此临时搭测试框架**:发现 1 那类 bug 单测也抓不到
(它在 mock 下不存在),而搭一套组件测试环境会引入 vitest 版本与 jsdom 配置的额外风险。
**建议单独立项**(并考虑新增 `pnpm --filter @fcp/web test:e2e` 之类的真实后端冒烟脚本),
已登记进 `PENDING.json`。

### 风险:新增了一个前端依赖

`qrcode@1.5.4`(+ `@types/qrcode`)。它的 npm 包声明依赖 `pngjs` / `yargs`,但**浏览器入口**
(`lib/browser.js`,package.json 的 `browser` 字段已指向)不需要它们,构建产物也证实了这一点
(独立 chunk 仅 25.8 kB)。若将来要去掉这个依赖,替代方案是自己实现 QR 编码(约 200 行),
**不推荐** —— 自写 QR 编码是"看起来简单、错误只在特定内容长度下出现"的典型。

## 7. ★ 给下一个接手者的交接建议

**先读这三个文件**:

1. `apps/web/src/components/InviteCard.tsx` —— 文件头写了两条**刻意的**行为(为什么非成员不能看码、
   为什么过期码照展示),改之前先读
2. `apps/web/src/app/session.tsx` 的 `applyAuth` —— token 持久化的唯一位置,改动务必保持"先写 token"
3. `apps/web/src/api/config.ts` —— 开头的警告解释了 mock 模式的盲区

**接着做最省事的顺序**:

1. **前端单测基建**(已登记):web 的 `test` 是空壳。若要覆盖本轮改动,优先覆盖
   `api/mock.ts` 与 `api/client.ts` 的**纯逻辑**,组件测试次之。
   更值钱的是一个**真实后端冒烟脚本**:起 API → 用 HTTP 跑注册/建家/邀请码/加入,断言状态码。
   发现 1 那类 bug 只有它能抓。
2. **A7 邀请码轮换**:后端加接口,前端在过期提示处加"重新生成"按钮。
3. `media-proof.upload` + `points.prisma`:打通"派任务 → 评分 → 积分"闭环。

**别踩的坑**:

- **不要为了"少一个依赖"自己写 QR 编码**。见第 5 节风险段。
- **不要把 `qrcode` 改成静态 import**。那会把 10 kB 从按需变成首屏,违背本轮的拆分。
- **不要在 mock 模式下宣称前端"完成"**。mock 不校验 token,鉴权类问题在它下面完全不可见 ——
  本轮的 bug 就是这么活下来的。
- **`FamilyPage` 里的 `canShare` 只是省一次无用请求,不是权限控制**。真正的判定在服务端
  (`#10b` 会回答 403 `role_not_allowed`),前端永远不要把它当成安全边界。
