### 3.1 四个接口已按冻结契约实现,签名零改动

`join` 用 200 而不是 201:加入是**幂等**的(见 3.3),重复加入什么都没创建,回 201 有一半时候是假话。

路由以 `{ prefix: '/api' }` 挂载,**不是你原来注释里写的那样直接 `app.register(familyRoutes, …)`**:
为了让 `server.ts` 后续能拿到 `app.family` 去接 Prisma 与目录端口,我加了一层 `registerFamily(app, options)`,
它 `app.decorate('family', service)` 之后再挂路由 —— 和你的 `registerAuth(app)` 是同一个形状。
这是 `routes/index.ts` 里唯一需要你 review 的一处判断。

### 3.2 ⚠️ 跨车道时序:认证守卫在**请求期**解析,未就绪时回 503

`app.requireAuth` 由车道 A 的 `registerAuth()` 装饰在**根实例**上,而它当时还在 `feat/auth-register`(PR #1),
`main` 上没有。两种显而易见的做法都是错的:

- `{ preHandler: app.requireAuth }`:装饰器不存在时 Fastify 把 `undefined` 当成"没有钩子",
  **四个接口会变成完全公开**。不可接受。
- `import '../auth/middleware.js'`:本分支立刻无法 typecheck、无法独立合并,正是要避免的事。

所以守卫在**每次请求时**查找:`registerAuth(app)` 一旦跑过就自动生效,零代码改动。在此之前四个接口回
**503 `auth_unavailable`**,服务器照常启动。两条分支都有用例覆盖(`http.test.ts` 第一个 describe)。

**合并后请做一件事**(写给下一个动 family 的人):把 `routes/family.ts` 里本地的
`VerifiedAuthContext` / `currentUserId` 换成 `import { currentUserId } from '../auth/index.js'`,
并删掉那段本地声明。它现在的存在只有一个理由:车道 A 未合并。

### 3.3 契约没写死的地方,我选了这些默认值(报告"需要决策"节有同样一份)

| 场景 | 行为 | 理由 |
|---|---|---|
| 邀请码不存在 / 格式非法 | `404 invalid_invite_code` | 两者回同一个答案,不给"猜格式"的反馈 |
| 邀请码过期 | `400 invite_expired` | A2 的"带有效期"必须可被用户理解 |
| 非成员访问 `:fid` / 家庭不存在 | **一律 `403 not_a_member`** | 刻意不区分,避免用 fid 探测某个家庭是否存在 |
| 重复加入 | **幂等**:200 + 已有 `{family, membership}` | 家人重复点"加入"是常态,409 会显示吓人的错误 |

## 附录:本轮踩的三个坑

### 事故 1:邀请字符表实际只有 31 个字符,而注释声称 32

- **怎么发现的**:写"字符表必须是 32 个,这样 `byte & 31` 才无偏"这条用例时它挂了 ——
  实际长度是 31,因为我漏掉了 `L`。
- **为什么危险**:注释里写着"32 是 2 的幂,所以取模无偏",而代码是 31。取模偏差本身影响极小
  (家庭邀请码不是密码学边界),但**注释与代码不一致**会让下一个读它的人做出错误推理。
- **修复**:字符表补上 `L`(`23456789ABCDEFGHJKLMNPQRSTUVWXYZ`),长度用例保留,现在真的会挡人。
- **教训**:凡是写进注释的"数学性质",都要有一条用例去证明它,否则它就是一句愿望。

### 事故 2:内存仓储用 `new Date()` 而不是调用方注入的时钟

- **怎么发现的**:`joinedAt` 的断言期望 `2026-03-01T10:00:00.000Z`,实际拿到当前墙上时间。
- **根因**:`createFamily` 在仓储内部取 `new Date()`,绕过了本来就注入好的 `clock`,
  于是"时钟可注入"这个设计在创建路径上**是假的**。
- **修复**:`CreateFamilyInput` 增加 `createdAt`,由用例从注入时钟取;家庭创建与所有者入会
  共用同一时刻(创建即入会)。Prisma 适配器同步。
- **教训**:"可注入时钟"必须覆盖**每一条**写时间戳的路径,漏一条就等于没有。

### 事故 3(非本模块,但会坑到每一个人):`docs/GITHUB-TOKEN-SETUP.md` 的做法在协作者场景下不可能成功

- **现象**:按该文档配置细粒度令牌,`Resource owner` 改成仓库所有者、`Only select repositories`
  里勾选仓库 —— 这两步**在界面上根本做不到**。
- **事实**(GitHub 官方文档 `managing-your-personal-access-tokens`,Fine-grained limitations):
  > Using fine-grained personal access token to **contribute to repositories where the user is an
  > outside or repository collaborator**.

  且经典令牌一节写明:only personal access tokens (classic) have **write access for public
  repositories that are not owned by you**。也就是说**协作者推别人的个人仓库,只能用经典令牌**;
  细粒度令牌的 `Resource owner` 只会列出你自己的账号与你所属的组织,永远不会有别人的个人账号。
- **本轮的处置**:按 AGENTS.md 铁律 —— **发现别人的东西有问题,只标注、不擅自改**。
  本轮**没有修改该文档**,已在报告的"需要决策"节请人类定夺。
- **建议**:把该文档开头改成"协作者推他人个人仓库 → 只能用经典令牌(勾 `repo`)",
  并附上官方 limitation 的原文引用,否则每个新协作者都要在这上面浪费半小时以上。
