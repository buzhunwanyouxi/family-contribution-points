## 5. 阻塞与风险(需要谁配合)

### ★ 阻塞:GitHub 不允许带 `repo` 权限的经典令牌推送 workflow 文件

**实测报错**(git 通道):

```
! [remote rejected] main -> main (refusing to allow a Personal Access Token to
  create or update workflow `.github/workflows/ci.yml` without `workflow` scope)
```

**API 通道也走不通**:建 blob 成功(HTTP 201),但在建 tree 时被挡(HTTP 404 ——
GitHub 对越权的标准响应)。**所以没有绕路,只能由人给令牌加权限,或改走网页界面。**

**两条可选路径**:

| 路径 | 操作 | 代价 |
|---|---|---|
| **A(快)** | 现有经典令牌加 `workflow` 权限:https://github.com/settings/tokens → 该令牌 → 勾 `workflow` → Update token | 该令牌的权限变大(它已能写全部 `repo`);用完可再取消勾选 |
| **B(稳)** | 建一个**细粒度令牌**,只授权本仓库 + Workflows:Read and write;用一次性命令推那一个提交 | 多几步设置;**但仓库所有者自己用细粒度令牌是可行的**(第 5.1 节的限制只针对"别人的仓库") |

> **注意**:路径 B 不会影响协作者 —— `docs/GITHUB-TOKEN-SETUP.md` 里"协作者只能用经典令牌"的结论
> 针对的是 `sun-521-s` / `MIAO98J` 那种"仓库属于别人"的身份,他们**仍然只能用经典令牌**。

### 风险 1:CI 文件在跑通之前是"未经验证"的

本机已把 5 条命令**逐条跑过**(包括此前从未跑过的 `pnpm -r build`),但 GitHub runner 是 Linux,
与开发机(Windows)不同。首次推送将是对这个文件本身的第一次真实检验 —— **按第 8.5 节如实记录**。

### 风险 2:CI 绿了但没人看

CI 的价值取决于"红了会不会拦住合并"。当前 `main` **没有分支保护**,所以 CI 只是"通知",
不是"门禁"。等 CI 跑通后建议开启保护:要求 `verify` 通过才能合并到 `main`。

## 7. ★ 给下一个接手者的交接建议

**先读这些**:

1. `.github/workflows/ci.yml` —— 每条关卡后面都写了"为什么要它",照抄之前先读原因
2. `apps/web/vitest.config.ts` —— **`pool: 'forks'` 不是可选优化**。CI 上若把它去掉,web 测试会
   静默什么都不做(本机实测过),而 CI 会显示绿灯

**接着做最省事的顺序**:

1. **把 `ci.yml` 推上去**(需要 `workflow` 权限的令牌,见第 5 节),然后看 Actions 页面是否绿
2. **开启分支保护**:要求 `verify` 通过才能合并到 `main`。否则 CI 只是一份通知
3. `media-proof.upload` + `points.prisma`:打通"派任务 → 评分 → 积分"闭环

**别踩的坑**:

- **不要用"再加一个令牌"来解决权限问题**(除非确实需要):经典令牌加 `workflow` 勾选即可,
  用完取消。令牌越多越难管,本项目已经因为令牌栽过跟头。
- **`pnpm/action-setup` 的 version 必须与 `package.json` 的 `packageManager` 一致**,否则 pnpm 拒绝运行。
- **CI 里不要 `--no-frozen-lockfile`**。那会让 CI 悄悄修锁文件,掩盖"有人忘了提交锁文件"这种问题。
