## 5. 阻塞与风险(需要谁配合)

- **风险 1**:`settle()` 的"创始人超时兜底 + 补分覆盖重算"目前只有单向计算,**重算与冲正流水尚未实现**(W3-04 遗留),谁做积分模块时需一并处理。
- **风险 2**:证据 72h 删除的前置条件是"先结算后删除",这条跨了 `scoring` 与 `media-proof` 两个模块,**需要两个模块负责人先对齐调用方式**(建议:media 模块调用 scoring 的 settle 服务,而不是各自判断状态)。
- **风险 3**:数据库 provider 目前是 sqlite,若有人用到 sqlite 不支持的特性会阻塞生产切换(见 ADR-004)。

## 6. 如何验证本轮改动(给下一位 AI)

```bash
pnpm install
pnpm --filter @fcp/api test        # 期望:settle.test.ts 8 个用例全部通过
pnpm --filter @fcp/api dev         # 期望:api listening on http://localhost:3000
curl http://localhost:3000/health   # 期望:{"ok":true,...}

# 结算规则快速自检(40% × 3 分 必须等于 1.2)
curl -X POST http://localhost:3000/api/scoring/preview \
  -H "content-type: application/json" \
  -d '{"maxPoints":3,"scores":[{"scorerId":"dad","isOwner":true,"percent":40}]}'
# 期望:{"percent":40,"points":1.2,"settledBy":"owner","provisional":false,...}
```
