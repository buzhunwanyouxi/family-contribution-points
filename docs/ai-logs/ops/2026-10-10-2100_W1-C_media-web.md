### ⚠️ 阻塞项 1:`PROJECT_GUIDE.md` 的 F6 恒等式自相矛盾,需要人类拍板

文档里两处口径无法同时成立:

| 出处 | 原文 | 含义 |
|---|---|---|
| 4.6 **F6** | `累计获得 − 已消费 − 冻结中 = 可用余额` | 冻结**不属于**可用余额 |
| 4.6 **F7** | `可用余额 = 当前可用 − 冻结中` | 冻结**属于**当前可用,是其中的保留部分 |

如果按 F6 字面实现:`earned − spent − frozen === available`,那么"发布悬赏"这一动作就会
凭空改变 `available`(而实际上没有任何钱离开这个成员),账本立刻不自洽 —— 我在实现
`buildBountyPayout` 时正是撞上这个矛盾,才把问题翻了出来(见附录事故 1)。

**本轮的实现选择(唯一自洽的读法)**:

```
累计获得 earned   = 所有赚取流水之和(只增)
当前可用 available = earned − spent       ← 就是 Membership.points 列
已消费 spent      = 兑换 + 愿望投入 + 冲正(钱真正离开成员的部分)
冻结中 frozen     = available 的保留子集(C3 发布悬赏时保留,过期释放)

恒等式(F6):earned − spent === available        ← 由构造保证,所以 J7 对账才有意义
当前可花    :available − frozen                ← F7 的"余额 = 可用 − 冻结"
```

**需要决策**:接受上面这个读法,还是坚持 F6 字面?若接受,请把 `PROJECT_GUIDE.md` F6 的
公式改为 `累计获得 − 已消费 = 当前可用`,并在 F5 补一句"冻结是可用余额的保留子集"。
**在人类回复前,请不要在其他模块另写一套口径** —— 实现只有 `apps/api/src/points/ledger.ts` 一处。

### ✅ 阻塞项 1 已裁决(2026-10-10,产品负责人)

负责人选择**方案 1**:冻结是"当前可用"的保留子集。F6 恒等式正式改写为:

```
累计获得 earned   = 赚取类流水 − 冲正流水
已消费   spent    = 兑换 + 投入愿望 + 悬赏支付

冻结中   frozen   = available 中被预留的子集

```

裁决前我先按原 F6 字面实现并**实测跑了一遍**,结果是 5 个悬赏相关用例全部失败:

`available` 凭空加回分数,而这份分数只能来自**降低 `earned`** —— 直接违反 F4(累计获得只增)。
三条规则 F4 / 原 F6 / C3 数学上不能同时成立,必须放弃一条。

## 附录:本轮踩的三个坑(建议后来者照抄结论)

### 事故 1:发现 F6 恒等式自相矛盾(有正面价值的"事故")

- **怎么发现的**:写赏金生命周期测试时,`buildBountyPayout` 让冻结减少却没有对应的余额减少,
  对账当场差了 8 分。顺着往上追,发现是文档两处口径冲突,而不是代码 bug。
- **处理**:按 AGENTS.md 铁律 —— **不自行改需求**。选定唯一自洽读法实现,把矛盾写成
  本文件的阻塞项上报人类,并在 `ledger.ts` 顶部用醒目注释标注"若人类另作决定,只改这一个文件"。
- **教训**:规则冲突不要"绕过",要"上报";测试写得细,冲突会自己浮出来。

### 事故 2:Vite dev server 在 Windows 上被文件监听器搞崩

- **现象**:编辑 `styles.css` 时 dev server 直接退出,`EBUSY: resource busy or locked, watch '...\.styles.css.<pid>.<guid>.tmpdir\styles.css.tmp'`。
- **原因**:编辑器/Agent 写文件时会创建短命的 `.*.tmpdir` 目录,Vite 的 watcher 去监听它,随即被删除 → 句柄失效 → 进程退出。
- **修复**:`apps/web/vite.config.ts` 增加
  `server.watch.ignored = ['**/.*.tmpdir/**','**/*.tmp','**/node_modules/**','**/dist/**']`。
- **教训**:Windows 上多人协作,dev server 会因为临时文件崩,提前 ignore 掉。

### 事故 3:浏览器窗口不可见导致定时器被冻结,把排查带偏了 40 分钟

- **现象**:自动化验证时,点击按钮后界面停在"请稍候…",`setInterval` 计数恒为 0,
  看起来像"主线程被同步死循环占死"。
- **真相**:`document.visibilityState === 'hidden'`(浏览器窗口在后台),
  **Chrome 对后台页面会把定时器完全冻结**;而我通过 CDP 在隔离世界执行的同步 JS 照样能跑。
- **教训**(写进团队约定):
  1. 用浏览器做自动化验证前,先断言 `document.visibilityState === 'visible'`,否则结论不可信;
  2. "定时器不跑 + 同步 JS 能跑" ≠ 死循环,先查可见性;
  3. 窗口在前台时,同样的操作是**成功**的:登录后正确渲染出三个数字 86.4 / 42.4 / 44,
     说明功能本身没问题。
