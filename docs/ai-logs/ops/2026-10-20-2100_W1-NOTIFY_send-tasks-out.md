### ★ 发现 1(本轮的直接原因):台账里躺着需求,但**没有任何人收到通知**

用户问了一句"你给其他人发需要协作的任务没",我去核实,结果是:

|---|---|
| `PENDING.json` 里给 A/B 的任务 | **2 条**,挂了 4–7 天 |
| 独立 issue | **0 条** |
| 唯一的 issue(#4,10-13) | 是"请读收件箱"的**公告**,只在正文里顺带提了两件事 |
| **#4 的 2 条评论** | **都是我发的,他们一个都没回** |
| `sun-521-s` 最后活动 | 2026-10-12 |
| `MIAO98J` 最后活动 | 2026-10-13 |

**结论**:这套机制一直在**自言自语**。台账→收件箱这条路是通的,
但**收件箱不会主动通知任何人** —— 它需要人去读。而我从来没有把"去读"这件事推到他们面前。

> **这正是那条 `must-know` 说的**:
> 「所有'要人拍板'的事都靠 GitHub @ + 指派触发邮件;不要把协作需求只发在仓库里,那等于没发。」
> **规则写在那里,我自己没照做。**

### ★ 发现 2:"公告型 issue"不是有效的通知形式

`#4` 的教训值得写下来 —— 它有 7 天时间、指派了两个人,却**零回复**。三个原因:

| 缺什么 | 后果 |
|---|---|
| **没有具体动作** | 读者不知道要干什么,于是什么都不干 |
| **没有判据** | 做完了也不知道算不算完成 |
| **没有结论要求** | 可以"看过就算了",而系统不会发现 |

**新的三条 issue 每条都强制要求一句话结论**(改/不改、接/不接),
并在正文里写明"**只回'收到'不算结论**" —— 这是 `CONTRIBUTING.md` 第 5.1 节已有的规矩,
但**规矩只在被引用时才有用**。

### ★ 发现 3:MVP 的关键路径**从来没有被派给任何人**

`OWNERS.md` 的「下一步认领清单」有 9 项、标了建议车道,但:
- 它写在**认领表里**,而认领表需要人主动去看
- 三处(`CONTRACTS` / `OWNERS` / `ROADMAP`)**都说"待认领"**,却**没有任何机制把它推给人**

所以 `Issue #7` 的性质与 #5/#6 不同:**它是征集,不是指派** —— 我不能把没人同意的工作指派出去。
但至少要**让人知道有这回事,并且知道代价**(不做则积分永远为 0、MVP 到不了)。

### 风险:三条 issue 可能仍然无人回复

这是**通道问题,不是内容问题**。我能做的:
① 发到唯一有效的通道(@ + 指派 → 邮件);
② 每条都要求结论而不是"收到";
③ 在 `PENDING.json` 里记下通知渠道,便于后续追踪。

**但我无法保证他们会回。** 如果一周后仍然零回复,那说明**问题在通道本身**
(邮件被忽略 / 他们不看 GitHub),届时应升级到"离线沟通 + 由人拍板是否继续等"。

## 7. ★ 给下一个接手者的交接建议

**先读** `docs/coordination/PENDING.json` 里带 `📣` 的那两条 —— 它们记录了这个需求**通知到哪了**。

**接着做**:

1. **等 A/B 的结论**。如果一周仍无回复,**不要重复发 issue**(重复 = 噪音),
   应当由人决定:换通道、或直接自己做
2. 如果 `#7` 无人接,**发起人自己做 `TaskInstance`** —— 关键路径空着比做错更糟
3. **以后每加一条给别人(或给自己)的待办,顺手问一句"这条通知发出去了吗"**

**别踩的坑**:

- **不要用"公告型 issue"派活**。必须有:具体动作 + 做完的判据 + 一句话结论的要求。
- **不要只说"请读收件箱"**。读者不知道读了要干什么;要把**那件事本身**写进 issue。
- **不要在 issue 里定义新规则**(`CONTRIBUTING.md` 5.1 第 2 条)。一律指向 `docs/` 的出处。
- **不要为了通知而新增 `PENDING.json` 字段**。字段约定是禁令 8 管辖的约束文件,
  本轮用 `note` 里的 `📣` 标记即可。
