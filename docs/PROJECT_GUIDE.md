## 1. 原始创意(用户原话整理,保留原始设计意图)

> 用户可以自己创建一个家庭,用户手机号或者邮箱注册账号,用户注册好后可以创建家庭,设置好家庭账号、密码,其他用户可以加入,比如说子女、配偶、父母啥的注册好个人账号后输入家庭密码和账号即可加入家庭。
>
> 家庭创始人可以创建每天定时劳动任务,比如 14 点洗碗、11 点洗菜、10 点买菜,每个任务都有积分。每个每天的日常劳动任务必须有人接取,比如日常扫地、洗碗。每个家庭成员也可以在某天自己发布个任务,比如今天母亲有事,给哥哥布置个接弟弟放学的限时任务,也有积分。比如弟弟今天做题碰到不会的,可以在家庭任务发布个辅导自己做题的限时任务。

**从这个原始创意里提炼出四个真正的差异点**(这是产品最值钱的部分,后续开发不要削弱它):

1. **双向任务市场** —— 不是"家长管孩子",而是全家人互相派活:母亲派哥哥接弟弟、弟弟发题求辅导、姐姐攒分换 iPad。
2. **固定任务 + 临时任务双轨** —— 固定任务是家庭的"日常基线",临时任务是"今天的意外"。
3. **家庭内部经济** —— 积分是家庭内部流通的"劳动货币",有产出(做任务)、有消费(兑愿望)。
4. **成员自定义愿望** —— 兑换目标不是平台预设的,而是这个家庭自己商量出来的(弟弟要 iPad、妈妈要一次全身按摩、爸爸要一个不用做饭的周末)。

## 2. 产品定位与边界

### 2.1 一句话定位

**把家务从"父母的唠叨"变成"家庭内部的公平游戏":谁做了、做得多好、值多少分、能换什么,全家都看得见。**

### 2.2 目标用户与角色

| 角色 | 典型人物 | 特征与诉求 | 界面要求 |
|---|---|---|---|
| 创始人 owner | 父亲 / 母亲 | 掌规则、定分值、**必须评分**(裁判长);可能上班不在家 | 需要"评分中心""批量评分"高效后台 |
| 共同管理员 admin | 配偶、成年的子女 | 【补充】避免创始人单点故障 | 权限近似创始人,但不能改固定任务 |
| 普通成员 member | 配偶、父母、成年子女 | 接任务、发临时任务、参与可选评分 | 标准移动端 |
| 子女 child | 中小学生 | 积分驱动强、最在意愿望橱窗和排行榜 | 【补充】任务地图/进度条/奖励橱窗,正向激励为主 |
| 长辈 reader | 爷爷奶奶 | 不太会用 App、需要大字号和语音 | 【补充】大字号 + 语音报读 + 一键完成 |

### 2.3 设计原则(五条不可违背)

1. **正向激励优先**：只做加法,违规只记入"履约记录"并触发冷静期,**不设负积分、不扣已有积分**,避免孩子直接弃疗。
2. **透明可审计**：每一分都必须能查到"谁给的、为什么、什么时候",积分只追加不修改(冲正另记一条)。
3. **规则可被现实推翻**：任何规则都要有"豁免/暂停/请假"出口,否则家人会在线下无视它。
4. **不打扰**：每天推送不超过 2 条,汇总式提醒优先于逐条轰炸。
5. **温度 > 效率**：不做 KPI 考核式的监督、不做照片 AI 审查、不公开羞辱最后一名。

### 2.4 明确不做(第一期)

| 不做的事 | 原因 |
|---|---|
| 支付 / 提现 / 现金结算 | 合规风险 + 把亲情变雇佣关系 |
| 站内聊天 / 朋友圈式动态 | 家人本来就有微信群,重复建设 |
| AI 识别"碗洗得干不干净" | 技术不可靠,且会让家人反感(被机器监视) |
| 原生安卓 App / App Store 上架 | 成本高、门槛高、安卓碎片化,收益为零 |
| 多家庭社交 / 排行榜跨家庭 PK | 偏离核心场景 |
| 复杂等级体系 / 微服务架构 | 家庭级数据量(几 MB),单体足够 |
| 信用分 / 等级分等第二套评分体系 | 【v1.2 决定】与积分功能重叠、增加理解成本,已删除;违规只用"履约记录 + 冷静期"约束 |
| AI 直接改代码而不写操作日志 | 【v1.2】多人多 AI 并行时必然产生冲突代码,详见第 14 章 |

## 3. 已拍板的三项核心决策(用户确认)

### 决策 1:积分可兑换物品由**家庭成员自定义**【已定】

- 每个家庭成员(含创始人)**都可以**自定义商品/愿望并提交。
- 例如:弟弟在愿望单里新增"一台 iPad",**父亲(创始人)填写这个 iPad 需要 1000 积分**。
- 【补充】因此愿望商品需要一个"**定价与审核**"环节:成员提议 → 创始人(或管理员)审核并填写所需积分 → 上架到"愿望橱窗"。
- 【补充】定价权归创始人/管理员(它有家庭财政属性);普通成员负责"想"和"攒"。
- 【补充】愿望分值确定后**不可下调**(防止孩子攒到一半被涨价),只能上调且需家庭通知。
- 【补充】支持**多人共同攒分**(弟弟 600 + 姐姐 400 = 1000),也支持一人独攒。

### 决策 2:日常固定任务**只能由家庭创始人创建**【已定】

- 固定任务 = 每天/每周重复的日常家务,如"午饭后打扫卫生""清洁餐具""10 点买菜""11 点洗菜""14 点洗碗"。
- 只有创始人能新建、修改、停用固定任务;其他成员**只能接取和执行**。
- 【补充】固定任务不可以"删除"历史,只能**停用/暂停**(保留历史评分记录)。
- 【补充】创始人可设置:执行时间、重复规则、最高分、**谁能接**(全家/仅子女/仅指定人)、接取模式(**抢单** 或 **轮值**)。
- 【补充】临时任务**任何人**都能发(这是原始创意的亮点),但要有配额与悬赏上限(见 4.3)。

### 决策 3:评分 = **完成度百分比 × 任务最高分**,创始人必评、其他人选评【已定】

用户原话规则:

> 每个任务可以定个最高积分,比如洗碗最高积分 3 分。今天弟弟接了,打扫得非常好,参与评分的家庭成员一致给了完成度 100%,弟弟直接获得 3 分。第二天弟弟接了却开始敷衍,参与评价打分的家庭成员平均分只有 40%,弟弟最终只得了 1.2 分。
>
> 对于裁判系统:**家庭创始人必须打分**,其余家庭成员可以自己选择是否打分。打分只能打完成度,多个家庭成员打分**取平均值**。提示语:"您认为此次任务完成情况如何 ____ %",只能填 **0-100**,按百分比乘以该任务最高可得分。

**规则形式化**:

```
实得积分 = 完成度百分比(评分人平均值) × 该任务最高分

结算优先级:
  1) 创始人已评分        → 采用【创始人的百分比】(创始人是裁判长,一票定音)
  2) 创始人未评、他人已评 → 采用【其他评分人的算术平均】
  3) 无人评分            → 触发兜底(见 4.4 兜底规则)
```

**同时支持:接任务的人已在家完成任务,而创始人还在上班** → 成员把**图片/视频上传到"今日任务"里**,其他家庭成员看到证据后打分。创始人下班后再补评分/覆盖。

### 4.3 临时任务(家庭成员自发布,产品的灵魂)

| 编号 | 需求 | 来源 |
|---|---|---|
| C1 | 任何成员可发布临时任务:标题、说明、截止时间、悬赏积分、最多几人接 | 【原创意】 |
| C2 | 示例场景:母亲给哥哥发"今天 17:30 接弟弟放学"、弟弟发"辅导我做完这道题" | 【原创意】 |
| C3 | 【补充】**防滥用配额**:每人每天最多发 3 条;单条悬赏 ≤ 50 分;悬赏分从发布者余额中**预冻结** | 【补充】 |
| C4 | 【补充】接取人可以**拒绝**,但必须填写理由,且计入履约记录;小任务可"议价" | 【补充】 |
| C5 | 【补充】发布者**不得**要求金钱、不得有不安全内容、不得强制他人放弃休息时间 | 【补充】 |

### 4.4 接取、执行与履约

| 编号 | 需求 | 来源 |
|---|---|---|
| D1 | 任务在任务池可见,接取后状态变"已接取",其他人不可重复接 | 【原创意】 |
| D2 | 【补充】**接取后 15 分钟内可无责退单**;超过 15 分钟放弃只记一次"弃单"到履约记录,**不扣积分**;连续弃单会触发 7 天冷静期 | 【补充】 |
| D3 | 【补充】到截止时间未完成 → 自动释放回任务池 + 记一次"未履约" | 【补充】 |
| D4 | 【补充】连续 3 次未履约 → 该成员 7 天内不得接同类任务(冷静期) | 【补充】 |
| D5 | 【补充】**到期兜底指派**:截止前 30 分钟仍无人接 → 通知所有成员;到点仍无人接 → 系统强制指派给"本周贡献最低 + 当前空闲"的成员,并标记"被指派"(只是提醒,不扣分) | 【补充】 |
| D6 | 完成后上传**照片 / 视频**作为证据,进入"待评分" | 【已定】 |
| D7 | 【补充】证据要求:拍照或录像(网页可直接唤起相机);图片前端压缩到约 300KB;视频限 15 秒 / 20MB | 【补充】 |
| D8 | 【已定】**证据只保留 3 天(72 小时)**:照片与视频自上传时刻起 72 小时内可查看,超过 72 小时由系统自动删除,**不再占用存储** | 【已定 v1.2】 |
| D9 | 【补充】**到期提醒必须做**:上传成功时提示"证据保存 3 天";剩余 24 小时与剩余 6 小时各提醒一次(提醒上传者 + 提醒尚未评分的人);任务卡与证据页显示"剩余 XX 小时"倒计时;过期后显示占位图"证据已到期自动删除" | 【补充 v1.2】 |

### 4.5 评分与结算(核心中的核心)

| 编号 | 需求 | 来源 |
|---|---|---|
| E1 | 评分界面提示语固定为:**"您认为此次任务完成情况如何 ____ %"**,数字键盘,仅允许 0-100 | 【已定】 |
| E2 | **创始人必须评分**;其他家庭成员**可以选择是否评分** | 【已定】 |
| E3 | 多人评分**取平均值**;实得积分 = 平均完成度% × 任务最高分 | 【已定】 |
| E4 | 结算优先级:创始人已评 → 用创始人的分;创始人未评 → 用其他人的平均分 | 【补充】 |
| E5 | 【补充】**评分下限 30%**:低于 30% 视为"明显没做",走**驳回**流程(不进百分比评分) | 【补充】 |
| E6 | 【补充】**取整规则**:百分比按 **5% 为步长**取整(30/35/…/100),避免出现 1.83 分这种让人焦虑的小数 | 【补充】 |
| E7 | 【补充】**评分窗口 24 小时**,过窗口即锁定,防止事后翻旧账改分 | 【补充】 |
| E8 | 【补充】**创始人超时兜底**:创始人 24 小时未打分 → 该次以其他成员平均分结算;创始人补分后**覆盖重算**(积分流水记一条冲正,不删原记录) | 【补充】 |
| E9 | 【补充】**完全无人评分** → 按最高分 **60% 暂计**,创始人补分后多退少补 | 【补充】 |
| E10 | 【补充】创始人待评分任务**汇总推送**(如"你有 3 个任务待评分"),可**批量一键评分** | 【补充】 |
| E11 | 【补充】**评分人不能是受益人自己**;利益相关(如被辅导者给辅导者打分)采用互评 | 【补充】 |
| E12 | 【补充】**申诉机制**:评分后 24 小时内可申诉,由其他管理员复核或全家投票 | 【补充】 |
| E13 | 【补充】**驳回**的任务可以重做(回到"进行中",截止时间顺延) | 【补充】 |
| E14 | 【补充 v1.2】**评分窗口(24h)与证据保留期(72h)是两条独立的时间线**:证据删除**不阻塞**评分与结算,仍可按规则评出百分比;但证据删除后**不能再以"证据"为由申诉** | 【补充 v1.2】 |

**结算伪代码(开发按此实现)**:

```
function settle(instance) -> points:
    if instance.status != '已完成待评分': return error

    ownerScore   = scores.find(s => s.is_owner == true)
    others       = scores.filter(s => s.is_owner == false)

    if ownerScore:                       # 创始人已评分一票定音
        percent = roundTo5(ownerScore.percent)
    elif others.length > 0:              # 其他成员平均
        percent = roundTo5(avg(others.percent))
    else:
        percent = 60                     # 完全无人评分兜底

    percent = clamp(percent, 30, 100)
    points  = round2(percent / 100 * task.max_points)

    if instance.final_points > 0:        # 覆盖重算
        ledger.append(duplicate(instance), -instance.final_points)  # 冲正
    ledger.append(instance, +points)
    instance.final_points = points
    instance.status = '已完成'
    user.points += points
```

### 4.10 媒体证据生命周期(【已定 v1.2】,实现细节)

> **一句话规则:任务证据照片/视频只活 72 小时,到期自动删除,删除前必须提醒。**

| 阶段 | 时间 | 系统行为 |
|---|---|---|
| 上传 | T+0 | 写 `ProofMedia.expire_at = uploaded_at + 72h`;界面提示"证据将保留 3 天,请及时评分";卡片显示"剩余 72 小时" |
| 待评分期 | T+0 ~ T+48h | 首页与评分中心显示倒计时;评分人打开证据页可全屏查看/下载(下载仅限家庭成员) |
| 到期前 24h | T+48h | 推送提醒:"弟弟的洗碗证据将于 24 小时后自动删除,尚未评分的请尽快查看" |
| 到期前 6h | T+66h | 二次提醒(合并进当日汇总推送,不额外增加推送条数) |
| 到期 | T+72h | 执行删除(见下方删除流程),`ProofMedia.status` 置为 `已过期`,`deleted_at` 记录时间,**数据库保留一条元数据**用于审计(谁上传的、什么时候、什么类型),但**文件本体与缩略图从对象存储删除** |
| 到期后 | > T+72h | 任务详情显示占位卡"证据已于 X 月 X 日到期自动删除";任务与积分记录照常保留,不受影响 |

**删除前置条件(必须同时满足才允许物理删除)**:

1. 该任务/实例**已结算**(`status = 已完成` 或 `已驳回`),或已过结算兜底时限(24h);
2. 申诉窗口已过(24h)。

若时间冲突(如创始人一直不评分),**以"先结算、后删除"为原则**:到期时若尚未结算,则自动触发 `settle()` 兜底结算,然后立即删除证据。

**技术实现要点(给开发的硬性约束)**:

- 证据上传成功**即写入 `expire_at`**,不要依赖"先进先出"扫描;
- 到期删除用**定时任务**(每小时跑一次)+ **对象存储生命周期规则**(双保险,防止服务挂掉导致文件堆积);
- 对象存储桶默认生命周期设为 **4 天兜底**(比 72 小时多一天容错),真正的 72 小时精度由应用层定时任务保证;
- 删除操作必须是**幂等**的(重复执行不报错);
- 缩略图与原图都要删;CDN 缓存需要配置 `Cache-Control` 不超过 1 小时,避免"已删除但还能看到";
- 删除量与失败量写入日志,便于排查存储泄漏。

**保留期的取舍说明(为什么是 3 天)**:

- 覆盖完整的评分窗口:结算兜底 24h + 申诉窗口 24h = 48h,留 1 天余量;
- 家庭场景下照片/视频属于**隐私敏感内容**(含家庭成员尤其是未成年人影像),短期保留本身就是隐私保护;
- 家庭级应用的存储成本主要来自视频,**72 小时策略可以把存储量压到几乎可以忽略**。

## 5. 完整业务流程

```
【创始人】创建家庭 → 邀请家人
        ↓
【创始人】建固定任务(洗碗 / 每天 14:00 / 最高 3 分 / 必须有人接 / 抢单)
        ↓
【成员】在"今日任务"接单  ←── 到期未接 → 通知全员 → 强制指派给贡献最低者
        ↓
【成员】完成后上传照片 / 视频(可直接唤起相机,证据只保留 72 小时)
        ↓
【状态】待评分 ──→ 推送"待评分"给创始人 + 全员 → 证据倒计时提醒(剩 24h / 6h)
        ↓
【评分】创始人必评(0-100%) + 其他成员选评(0-100%)
        ↓
        ├─ 创始人已评  → 用创始人的 %
        ├─ 创始人未评  → 用其他人的平均 %
        └─ 24h 无人评 → 60% 暂计,创始人补分后覆盖重算
        ↓
【结算】平均% × 最高分 = 实得积分(如 40% × 3 = 1.2 分,入账并通知)
        ↓
【积分】累计获得 ↑ / 当前可用 ↑ / 已消费不变(可在积分页看到三个数字)
        ↓
【证据】上传满 72 小时 → 自动删除(数据库留元数据,文件本体销毁)
        ↓
【愿望】成员自定义 iPad(1000 分) → 创始人定价上架 → 全家攒分 → 创始人兑现
```

## 6. 产品形态与技术选型(最低成本方案)

### 6.1 核心结论:PWA 网页应用

**用户使用链路(家人视角)**:

> 爸爸把链接/二维码发到家庭微信群 → 妈妈点开 → 手机号登录 → 浏览器菜单"添加到主屏幕" → 桌面出现图标 → 点开全屏运行(没有地址栏)→ **以后自动更新,永远不用重装**

**为什么不做原生 App,也不做小程序(第一期)**:

| 需求项 | 是否真的需要原生 App |
|---|---|
| 拍照 / 录像上传、看照片评分 | ❌ 浏览器完全能做 |
| 定时提醒(14:00 洗碗) | ⚠️ 唯一的难点,但要靠**微信/短信**,不是靠 App |
| 多人协作、权限、积分流水 | ❌ 纯服务器逻辑,与客户端形态无关 |
| 上架应用商店 / 支付 / 蓝牙 | ❌ 不需要 |
| 全家各种安卓机(华为/小米/OPPO/vivo) | ❌ 越原生越麻烦 |

**三方案对比(仅针对本场景)**:

| 方案 | 开发成本 | 运维/上架成本 | 家人使用门槛 | 定时提醒 | 结论 |
|---|---|---|---|---|---|
| 微信小程序 | 中 | **高**:主体注册、个人主体受限、类目资质、认证费 | 最低(最熟悉) | 订阅消息(需每次授权) | ❌ 起步最贵,二期再考虑 |
| 安卓原生 App | 最高 | 高:签名、分发、部分手机装不上、改一次要重装 | 需"允许安装未知来源" | 最好 | ❌ 完全不值得 |
| **PWA 网页** | **最低** | **几乎为零**:部署一次,无上架无审核 | 点链接→加桌面,10 秒 | 靠微信/短信补 | ✅ **第一期选它** |

### 6.2 唯一的短板与解决办法:消息推送

国内安卓浏览器自带 Web Push 不可靠(华为/小米浏览器基本不支持;无谷歌服务 = 无 FCM)。因此**不要指望浏览器推送**,用三层兜底:

1. **微信模板消息(主推,免费)**:注册微信订阅号/服务号,先用**测试号**(完全免费、可加 100 个用户)让家人关注,定时任务提醒直接进微信。
2. **短信(付费但极便宜)**:阿里云/腾讯云约 ¥0.045/条,只发"任务没人接""今天还没人洗碗"这类关键告警,一年不到 ¥10。
3. **零成本兜底**:首页"今日任务"红点 + 家庭微信群互相 @。

### 6.3 技术栈(建议)

```
前端   PWA 单页应用:React + Vite + Vant(移动端组件库)
       一套代码 → 安卓 / 苹果 / 电脑浏览器全部可用
后端   Node.js(Fastify)或 Python(FastAPI),单体服务
数据库 PostgreSQL(生产)/ SQLite(开发与自用;家庭级数据量几 MB,SQLite 足够)
文件   对象存储(腾讯云 COS / 阿里云 OSS),图片视频直传;任务证据配 72 小时过期 + 桶级 4 天生命周期双保险
推送   微信订阅号模板消息(免费)+ 短信(关键告警)
部署   腾讯云轻量 2核2G(活动价 ¥50~100/年),或 Cloudflare Pages + Workers(免费)
```

### 6.4 国内特有的坑:域名备案(必须提前知道)

国内服务器 + 自定义域名 **必须做 ICP 备案**(免费,需身份证 + 手机号核验,耗时 1~3 周)。三条路线:

| 路线 | 做法 | 成本 | 上线速度 |
|---|---|---|---|
| **A(推荐,最省心)** | 国内轻量服务器 + 备案域名 | ¥100~150 / 年 | 备案完成后(1~3 周) |
| **B(最快跑起来)** | Cloudflare Pages / 海外方案,不备案 | ¥0 | **当天**可用,国内访问偶尔慢 |
| **C(折中)** | 先用平台默认域名,后期再迁 | ¥0~50 | 快 |

**执行建议:先在本地/局域网跑起来给家人试一周,规则打磨顺了再花钱买服务器和备案。** 规则一定会改(现在已经改了三轮),不要为部署消耗时间。

### 6.5 移动端适配注意点

- **安卓适配策略**:Chrome / Edge / 华为 / 小米 / OPPO / vivo 浏览器全部按现代标准写;**"添加到主屏幕"入口各家不同**,首页要放一个"添加到桌面"引导(有 `beforeinstallprompt` 就自动弹,没有就给出各家操作图示)。
- **iOS**:用 Safari 分享菜单"添加到主屏幕"(引导文案要分开写)。
- **相机权限**:网页 `capture="camera"` 在安卓上可直接唤起相机;首次使用要给权限引导。
- **字体与无障碍**:长辈端提供大字号模式、高对比度、关键按钮语音报读。
- **离线**:PWA Service Worker 缓存首页与今日任务,断网也能看今天要做什么。


### 7.1 三条数据铁律

1. **积分只走流水表**(`PointsTxn`):任何积分变动必须有流水,任何修改必须用"冲正"而不是"改数";`PointsSummary` 只是可由流水**全量重算**的缓存。
2. **任务状态机单向流转**:`待接取 → 已接取 → 进行中 → 待评分 → 已完成`,另设 `已驳回 / 已放弃` 两个旁路;不允许跳回或倒退修改历史。
3. **验收人不能是受益人自己**:`TaskInstance.claimer_id ≠ Score.scorer_id` 必须在 API 层强校验;仅 owner 可写 `TaskTemplate` 同样在 API 层强校验。

### 7.2 定时任务清单(服务端必须实现,不允许依赖人工)

| 作业 | 频率 | 职责 | 相关规则 |
|---|---|---|---|

## 11. 风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| **规则僵硬被线下推翻** | "今天不用洗碗了""这周考试暂停" | 豁免/暂停/请假机制;节假日模式;创始人一键暂停 |
| **创始人不在线导致评分卡死** | 爸爸开会,弟弟的碗洗完 3 天没结算 | 24 小时兜底 + 覆盖重算 + 批量评分 + 待评分汇总推送 |
| **评分纠纷伤感情** | "我明明洗干净了,你只给 40%" | 证据(照片/视频)+ 申诉机制 + 评分下限 30% 走驳回 + 创始人一票定音但可申诉 |
| **证据删了才想翻案** | 第 4 天有人说"当时他根本没洗",但照片已删 | 证据页显示"有效期至 X 月 X 日",申诉窗口(24h)严格早于证据删除(72h);删除前 24h/6h 明确提醒"过期不可申诉" |
| **没人评分导致证据白删** | 爸爸出差一周,回来证据没了 | 24h 兜底结算强制先行,证据删除前必须先结算(见 4.10 前置条件) |
| **多人多 AI 并行写出互相矛盾的代码** | 两个 AI 各自实现了一套积分结算,规则不一致 | **强制 AI 协作规范(第 14 章)**:模块认领表 + 接口契约优先 + 每轮工作必须写操作日志与报告 + 禁止直接推 main |
| **抢分游戏化,谁快谁得分** | 大家抢轻松的活,难的没人接 | 轮值模式 + 兜底强制指派 + 贡献占比而非纯排名 |
| **临时任务被滥用** | "我给你 5 分,帮我写作业" | 每日配额 + 悬赏上限 + 可拒绝 + 内容红线 |
| **通胀/紧缩** | 积分发得太多没人稀罕,或攒不到目标就放弃 | 创始人定价权(总闸门)+ 愿望分值不可下调 + 保留 10% 储备分 |
| **长辈不会用** | 爷爷奶奶打不开链接 | 大字号 + 语音 + 一键完成;必要时由子女代操作 |
| **推送送不到** | 家人收不到 14:00 提醒 | 微信模板消息优先 + 短信告警 + 应用内红点 + 微信群人工 @ |
| **合规** | 未成年人数据、ICP 备案 | 积分不涉及真实货币、不设支付;数据仅家庭内可见;国内服务器必须备案 |

## 13. 术语表

| 术语 | 含义 |
|---|---|
| **固定任务 / TaskTemplate** | 由创始人创建的每日/每周重复家务,有固定最高分 |
| **任务实例 / TaskInstance** | 固定任务在某一天的具体一次,是接取、上传证据、评分、结算的对象 |
| **临时任务 / Task** | 任意成员随时发布的限时委托(接弟弟放学、辅导做题),带悬赏积分 |
| **最高分 / max_points** | 该任务的积分上限,如洗碗 3 分;实得 = 完成度% × 最高分 |
| **完成度 / percent** | 评分人给出的 0-100 整数百分比,系统取平均值(或创始人的值) |
| **创始人 / owner** | 家庭创建者,唯一能建固定任务、必须参与评分 |
| **共同管理员 / admin** | 创始人指定的助手,防止单点故障 |
| **履约记录 / Discipline** | 【v1.2】违规事实的记录(未履约、弃单、被驳回、破损),**不扣积分**;连续 3 次触发 7 天冷静期。原"信用分"机制已删除 |
| **累计获得 / earned_points** | 赚取类积分减去冲正后的净值,**除 E8 冲正外只增不减**;代表"一共为家庭贡献了多少",是荣誉口径 |
| **当前可用 / points** | `累计获得 − 已消费`,即真正能花的余额(F5);`当前可花 = 当前可用 − 冻结中` |
| **已消费 / spent_points** | 兑换奖励 + 投入愿望 + 悬赏支付的总额 |
| **冻结中 / frozen_points** | 【v1.3】**当前可用中被预留的子集**(不是额外的一笔钱);发布悬赏时预留,过期释放,完成时连同余额一起支付给执行人 |
| **历史累计发放额 / earnedTotal** | 只增不减的发放总额,用于徽章与月度报告,不参与 F6 恒等式 |
| **证据保留期 / PROOF_TTL** | 【v1.2】任务照片视频只保留 **72 小时**,到期自动删除,删除前有倒计时与提醒(见 4.10) |
| **AI 操作日志 / ops log** | 【v1.2】`docs/ai-logs/ops/` 下,面向其他 AI 的事实记录:改了什么、接口怎么变、遗留什么(见 14.4A) |
| **操作报告 / report** | 【v1.2】`docs/ai-logs/reports/` 下,面向人类操作者的说明:做了什么、怎么验证、有什么风险(见 14.4B) |
| **契约优先 / contract-first** | 【v1.2】跨模块接口以 `docs/CONTRACTS.md` 为准,先改契约再写代码 |
| **避免脑裂 / anti-divergence** | 【v1.2】多人多 AI 并行开发时,防止重复实现、规则矛盾、互相覆盖代码的一套协作纪律(见第 14 章) |

## 14. AI 协作规范(多人 + 多 AI 开源共创必读)

> **本章的产生原因**:本项目由 **3-6 名人类开发者 + 各自的 AI 编码助手**并行开发。实践中最容易出的事故不是"写不出功能",而是:
>
> 1. 两个 AI 各自实现了一套结算/积分逻辑,合并后规则互相矛盾;
> 2. 后来的人不知道前面的人改过什么,把已定的设计又推翻一遍;
> 3. 同一个文件被两路并发修改,合并冲突乃至覆盖丢失;
> 4. 人类操作者之间也互相不知道进度,重复劳动。
>
> **本章就是为了杜绝这些事故。任何 AI 在提交代码前,必须完成本章规定的日志与报告。**

**AGENTS.md 的写法要求(给 AI 看的第一入口)**:不超过 100 行,只写三件事 ——

② **硬性禁令**(不得绕过文档改规则、不得直接推 main、不得改契约而不更新 CONTRACTS.md、不得删改他人日志);

### 14.2 每轮工作的标准流程(AI 必须按顺序执行)

```
① 读    AGENTS.md → PROJECT_GUIDE.md(重点第 3、4、7、14 章)→ CONTRACTS.md → OWNERS.md → 最近 5 篇 ops 日志
② 查    在 OWNERS.md 找到目标模块:若"进行中"的负责人不是自己 → 停止,改做别的模块或先沟通
③ 认领  在 OWNERS.md 把该模块标记为"进行中:我(操作者名)/日期/预期产出",并写明所属需求编号(如 E1-E14)
④ 契约  若本轮要改动接口或数据表 → 先在 CONTRACTS.md 写清变更,再写代码(契约优先)
⑤ 实现  只改自己认领模块内的文件;共享文件的改动必须在本轮日志里显著标注
⑥ 自测  跑 lint + 单测;涉及结算、积分、过期删除的改动必须补上单元测试
⑦ 日志  写 docs/ai-logs/ops/<时间>-<任务号>-<模块>.md(模板见 14.4)
⑧ 报告  写 docs/ai-logs/reports/<同名>.md
⑨ 索引  在 docs/ai-logs/INDEX.md 追加一行
⑩ 提交  分支 feat/<模块>-<简述> → PR → PR 描述里贴日志与报告路径 → 等待人类审查
```

**第 ⑦⑧ 步是强制项,不是可选项。** 哪怕本轮什么都没做成(卡住了、需求不清楚),也必须写日志说明卡在哪,否则其他人会重复踩同一个坑。

### 14.3 AI 协作五条铁律

1. **文档优先于代码**:规则一律以 `PROJECT_GUIDE.md` 第 3、4 章为准。**AI 不得自行解释或简化规则**;发现文档自相矛盾或不可实现时,**先提 Issue / 先改文档**,禁止"代码里偷偷改一套"。
2. **契约优先于实现**:跨模块接口以 `CONTRACTS.md` 为唯一事实来源。**改了接口没更新契约 = 本轮工作无效**。
3. **模块归属唯一**:同一模块同一时间只能有一个负责人。不同 AI 可并行不同模块;**共享文件必须串行**(见 14.5)。
4. **日志只追加,不改写**:AI **只能新增**自己那篇日志,禁止修改或删除他人的日志;发现别人写错了,在自己日志里写"更正说明"并注明原文件名。
5. **不许静默放弃**:任何做不了的规则都要在日志与报告里写明"为什么做不到 + 建议的替代方案",由人类决策后回写文档。**"没实现"和"实现成别的样子"都必须留痕。**

### 14.5 防冲突机制(实测修订版,2026-10-12)

> ⚠️ **本节依据一次真实事故修订**:车道 A(PR #1)与车道 B(PR #2)各自**完全守规矩**地
> 按冻结契约完成实现,但把两个 PR **同时合并**时,仍在 **4 个文件**上产生了冲突:
> `apps/api/src/routes/index.ts`、`docs/CONTRACTS.md`、`docs/ai-logs/INDEX.md`、`docs/ai-logs/OWNERS.md`。
> 结论:**冲突不是纪律问题,而是并行开发的必然结果**;纪律的作用是把冲突从"两小时解冲突"压到"十分钟看懂"。

**新规则 0:先分片,再并行(2026-10-12 新增)**
"模块"这个粒度**太大**,会导致两个人先后改同一个模块目录。认领时按**子模块**(实现文件)粒度认领:

| 模块 | 子模块(可分别认领) |
|---|---|
| `auth` | `app`(路由装配+类型) · `service`(用例) · `password` · `jwt` · `middleware` · `repository`(内存) · `repository.prisma` · `errors` · `tests` |
| `family` | `app` · `service` · `invite` · `directory` · `repository` · `repository.prisma` · `errors` · `tests` |
| `media-proof` | `expiry`(纯逻辑) · `upload`(HTTP) · `storage` · `cron`(J4/J5) · `tests` |
| `points` | `ledger`(纯逻辑) · `prisma`(落库) · `routes` · `reconcile`(J7) · `tests` |
| `web-app` | `client`(API 客户端) · `pages/*` · `components/*` · `router/session` · `styles` |

**规则 0 的判定标准**:如果一个子模块的文件数 > 5 或改动会跨两个"层"(如同时改 HTTP 与数据库),
它就该继续拆 —— **拆到"一个人半天能做完"为止**。

**规则 1:模块认领表 `docs/ai-logs/OWNERS.md`**
每个模块一行,状态只有三种:`空闲 / 进行中 / 已完成`。


### 14.6 需要人来兜底的两个环节

AI 之间能靠日志对齐信息,但下面两件事必须由**人类操作者**拍板,AI 不得自行决定:
