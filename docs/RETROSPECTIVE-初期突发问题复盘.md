# 项目初期复盘报告:那些没预料到的突发问题

**项目**:家庭贡献评分奖励系统(开源共创,3 人 + 各自的 AI 助手)
**复盘范围**:项目从建仓库到第一位协作者提交 PR 的初期阶段
**当前状态**:13 次提交 / 69 个文件 / 45 个单元测试全绿 / 1 个协作 PR 待合并
**复盘目的**:重点记录初期规划完全没预料到、但实际推进中真实发生的问题,并给出可复用的对策

---

## 一、总体结论(先说要点)

| 结论 | 说明 |
|---|---|
| 最大的意外不是技术难度,而是"环境与平台" | 11 项突发问题里,7 项属于工具/网络/权限层,只有 2 项是代码逻辑问题 |
| 规划期最该补的文档,一份都没写 | 我们写了约 3 万字产品与技术文档,却没写"新人如何拿到上传权限"——结果第一位协作者的第一次提交就卡在这里 |
| "能不能推上去"是初期的头号工程风险 | 协作者推不上代码 + 主通道反复中断,合计消耗的时间远超任何功能开发 |
| AI 协作的风险不在"写错代码",而在"自作聪明" | 两次真实事故(远端目录被挤掉、本地工作区被清空)都不是写错逻辑,而是对"命令成功"的过度自信 |
| 靠纪律兜住了 | 已形成"推送前后双向核对"的习惯,最后一次跨平台写入做到 67 个文件逐一哈希匹配 |

## 二、突发问题清单

### A. 权限与账号类

#### A1. 协作者无法上传代码 —— 所有人都没预料到的"第一道墙"

| 项 | 内容 |
|---|---|
| 出现时机 | 协作者拿到任务、写完代码、准备推送时 |
| 现象 | 用细粒度令牌在 "Only select repositories" 里根本找不到本仓库 |
| 根因 | 细粒度令牌的 Resource owner 默认是令牌所有者自己,而仓库属于另一个账号;细粒度令牌只能授权"所选 resource owner 名下"的仓库 |
| 耗时 | 协作者卡住 + 来回确认约 40 分钟 |
| 解决 | 把 Resource owner 改为仓库所有者即可,不必换令牌类型;另附经典令牌与"完全不用令牌(系统凭据管理器)"两条备选路径 |
| 是否可预防 | 完全可以。初期应有一份"新人拿到仓库后的第一小时该做什么"清单,含环境自检与权限自检 |

#### A2. 本地完全没有可用凭据(AI 无法代跑权限操作)

- 探测结果:无 GitHub CLI、无环境变量令牌、无 SSH 密钥;系统凭据管理器里的记录不是标准 git 条目,自动读取失败。
- 后果:建仓库、发邀请、推送全部必须由人手工授权一次,AI 无法独立完成。
- 教训:规划期把"人 + AI 协作"当成了纯技术问题,漏掉了"凭据如何交给 AI 使用"这一环,也没有约定凭据的存放与撤销方式。

#### A3. 凭据处理踩到多个平台限制

- 用 OAuth 设备码登录失败:换取令牌时网络超时,重新生成设备码后再次超时。
- 命令行工具要求令牌含 `read:org` 权限,仅有 `repo` 会被直接拒绝登录。
- 最终退回 REST API + 临时把令牌注入远端地址的方式推送,并推完立刻把地址改回不含令牌的形式。
- 按邮箱邀请协作者无法通过 API 完成(平台只在网页界面提供),只能走浏览器界面。

### B. 网络与平台可达性类

#### B1. git 传输通道反复不可用,而 API 通道正常

| 项 | 内容 |
|---|---|
| 现象 | `github.com:443` 频繁连接超时/重置(单次 21 秒超时,连续 4~5 次失败);同一时刻 API 域名完全正常 |
| 后果 | 无法 fetch、无法 push;本地与远端一度相差多个提交 |
| 应对 | 改用 REST API 直接构造提交,并形成"推送前先断言本地 tree 与远端 tree 一致,不一致立即中止"的硬检查 |
| 现状 | 通道后来恢复,推送改回标准 git 方式 |

#### B2. 连"读取文件内容"的域名也会被拦

用于对比本地与远端内容时,内容直读域名连接超时,而 API 通道正常 —— 可达性要按域名分别判断,不能笼统认为"能上平台"。

#### B3. 平台网页端自身也会返回 5xx

核对文档是否上传成功时,网页端连续 504/503,而同一时刻 API 读取同一文件正常。结论:核对"是否真的上传成功"应以 API 与内容比对为准,不要依赖网页端能否打开。

### C. 工具链与本地环境类

#### C1. 用脚本批量生成含中文的源码文件,中文全部乱码

| 项 | 内容 |
|---|---|
| 根因 | Windows PowerShell 5.1 按系统本地编码(GBK)解析脚本文件;脚本内容虽是 UTF-8,中文被按 GBK 解释后写入目标文件 |
| 症状 | 配置文件出现"未闭合字符串"语法错误、数据模型文件出现行粘连;测试报错才暴露 |
| 附带收获 | 借机做了一个架构决定:持久化标识符一律用 ASCII(如 open / pending_score),中文只留在界面层 |
| 是否可预防 | 完全可以。规矩:只要目标文件含中文,就用原生 UTF-8 工具写入,不要用 shell 的 here-string 批量生成 |

同一个根因后来又咬了几次:脚本里出现中文全角引号会直接语法报错;写办公软件自动化脚本时又踩了两次。最后固定成一条规矩:**自动化脚本一律纯 ASCII,中文路径用字符码点拼**。

#### C2. 包管理器大版本行为变更,直接拦住构建

- 装依赖时报"忽略的构建脚本",关键依赖的安装脚本被拦截,导致客户端生成与测试启动异常。
- 根因:新版包管理器不再读取配置文件里的旧字段,配置迁移到了另一个文件,且键名与写法都变了。
- 教训:依赖升级后先查官方配置说明,不要照抄旧版本文档。

#### C3. 开发服务器因"文件监听"崩溃(Windows 特有)

- 编辑样式文件时开发服务器直接退出,报资源被占用。
- 根因:编辑器写文件时创建短命临时目录,文件监听器去监听它、随即被删除,进程崩溃。
- 修复:配置里显式忽略临时文件与目录。

#### C4. 换行符的潜在冲突(提前拦下)

多人跨平台协作时,Windows 默认会把换行改成 CRLF,导致整文件级别的伪改动。处理:仓库根目录加换行符规范,统一为 LF;后续核查协作者提交时确认关键文件 CRLF 计数为 0。

### D. 协作流程类

#### D1. 分工被线下对调,文档没同步,差点两人写同一块

- 现象:计划文档写 A 负责甲模块、B 负责乙模块,实际两人对调,而文档没改。
- 风险:其他人的 AI 读到过期分工,会去写别人正在写的模块。
- 处理:立即更新分工文档与模块认领表,并把"分工变更 = 改文档 + 提交,不能只在群里说"写成规则。
- 附带发现:平台显示名与登录名不是一回事(有人显示名带空格),文档一度写错,已统一以登录名为准。

#### D2. 第一天没人敢认领"权限最大的模块"

- 现象:最基础的账号模块无人认领,大家都在等"接口定下来"。
- 处理:由前端一侧先把接口签名冻结(含零依赖的接口客户端与假数据),让两条后端车道各有明确靶子,前端也不必等后端。
- 效果:协作者拿到冻结签名后一次做对,3 个接口的成功与失败形状与契约逐字段一致,且没有改动别人的模块。

### E. 两次真实事故(必须写进复盘)

#### E1. 用 API 手工提交时,把远端 40% 的文件挤掉了

| 项 | 内容 |
|---|---|
| 经过 | 因 git 通道不通,改用平台 API 构造提交;构造目录树时把改动文件平铺成了新的根目录结构,原本未改动的 38 个文件被整体挤掉 |
| 如何发现 | 推送后核对远端文件数,29 对本地 67,当场发现 |
| 修复 | 改为基于父提交的目录树做增量更新;并保留那个坏提交在一个明确命名的分支上作证据,不删除 |
| 新增防线 | 之后每次 API 提交都先断言本地 tree 与远端 tree 完全一致,不一致立即中止 |

#### E2. 强制重置把刚写完的文件清空了

- 经过:网络中断导致拉取失败,而仍执行了强制重置 —— 本地记录的远端引用还指向旧提交,于是工作区被退回上一个提交,刚写的 3 个文件与日志从工作区消失。
- 如何挽回:从引用日志里找到那个提交,完整恢复,并逐项校验内容。
- 新增防线:拉取未明确成功之前,绝不执行强制重置。

### F. AI 自动化验证中的"假象"

#### F1. 浏览器窗口被隐藏导致定时器冻结,被误判为"死循环"

- 现象:自动化点击后界面停在"请稍候…",页面内定时器计数恒为 0,看起来像主线程被死循环占死。
- 真相:页面可见性为 hidden —— 浏览器对后台页面会把定时器完全冻结,而通过调试协议在隔离环境执行的同步脚本照样能跑,于是"同步能跑 + 定时器不跑"被误读成矛盾信号。
- 代价:约 40 分钟排查,还顺手改了不该改的样式(后来回滚)。
- 新增规矩:做浏览器自动化验证前,先断言页面可见;并记住"定时器不跑不等于死循环"。

### G. 文档工程类(简历与文档生成也踩了)

| 编号 | 问题 | 根因 | 教训 |
|---|---|---|---|
| G1 | 整块单元格属性被当成正文写进了文本节点 | 正则 `<w:t[^>]*>` 会匹配到 `<w:tcPr>`(前缀相同) | 必须写成要求标签后有空格或右尖括号的严格形式 |
| G2 | 自评内容被塞进了"获奖情况"表 | 用"按内容查找"定位相同空行时,匹配到了另一张表的同名行 | 必须限定在目标表作用域内按索引拼接,不能用全局替换 |
| G3 | 删除文档末尾说明页时切坏了 XML | 按标题文字位置删除会切在节点中间 | 应锚定分页符,并加"删完必须能解析"的断言 |
| G4 | 表格行高压不下来 | 模板把最小行高写死在单元格属性里,改段落间距无效 | 压缩前先确认约束在哪一层 |
| G5 | 办公软件差异:一款导出 PDF 报参数类型错,另一款一次通过 | 未先探测本机默认处理器 | 自动化办公软件前先探测装了哪一款、谁是默认程序 |

## 三、规律提炼:初期为什么想不到这些

| 为什么会漏 | 具体表现 | 对策 |
|---|---|---|
| 把"人"当成了"账号" | 规划里只有"协作者加入即可开发",没有"加入后如何获得上传权限" | 上手清单要包含权限自检与第一个可验证的小任务 |
| 把"网络"当成恒定条件 | 默认 git 一定能推 | 关键节点双通道准备(git + API),且以内容比对为准 |
| 把"工具"当成不变的 | 包管理器、编码、办公软件的版本差异全部踩了一遍 | 环境清单 + 版本锁定 + 生成含中文文件时禁用 shell |
| 对 AI 的能力边界过于乐观 | 以为 AI 能独立完成权限类操作 | 明确"必须由人完成的动作清单"(授权、生成凭据、平台网页操作) |
| 把"命令成功"当成"做对了" | 两次事故都是命令返回成功但结果错误 | 结果导向的校验:文件数、逐文件哈希、tree 一致性 |

## 五、一句话总结

这个项目初期真正的成本不在功能开发,而在"让三个人、三台机器、三个 AI 能互相看见,并且真的把代码传上去"。产品与技术文档我们写得很足,但缺了最朴素的一页 —— 新人怎么拿到权限、怎么验证自己通了。

而 AI 带来的新风险也不是"写错逻辑",而是"命令成功即认为做对"。补上结果导向的双向校验之后,风险立刻可控。
