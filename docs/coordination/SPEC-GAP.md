# 规则缺口(spec-gap):让 AI 提出规则改进,但不许自己改规则

> **一句话**:AI 负责**发现**规则不够用,人负责**决定**加什么规则。
>
> 本机制是协作消息总线的第四种条目类型。账本是 [`PENDING.json`](PENDING.json),
> 生成器是 [`../../scripts/sync-inbox.mjs`](../../scripts/sync-inbox.mjs)。

---

## 一、它解决什么问题

项目的规则(协作规范、检查项、模板、字段约定)不可能一次设计对。
真实情况是:**每一条规则都是撞到第一个反例之后才定型的。**

回顾本项目自己的三条规则,没有一条是设计出来的:

| 规则 | 它是怎么来的 |
|---|---|
| 认领要拆到**子模块** | 10-12 两个 PR 合并预演,撞上 4 个共享文件冲突 |
| 收工"自测"要拆成**三件互不替代的事** | 10-13 发现"自测"没覆盖"反查收件箱" |
| 信号要**双向**(出现 + 消失) | 10-13 发现解锁表现为"删除",只监测新增会丢信号 |

**但当时这些发现都是人想出来的。** AI 撞到规则不够用时,它有两个坏选择:

- **默默绕过** → 缺口没人知道,下次还会撞
- **自己改规则** → 见第二节,这是绝对禁止的

**本机制提供第三个选择:记录下来,交给人。**

---

## 二、唯一的红线:被约束者不得修改约束

> ⚠️ **禁止 AI 修改自己的 spec。**

原因不是"AI 不可信",而是**激励方向错了**:任何约束系统,如果被约束方能修改约束,
约束就会衰减到零 —— 因为"这条检查太麻烦"永远是一个看起来合理的修改理由。

这与本项目已有的两条规则一致:

- `AGENTS.md` 禁令 1:**禁止自己发明产品规则**
- `PROJECT_GUIDE.md` 第 14 章:**规则只能由人类拍板**

**本机制把这条原则从"规则文件"扩展到"规则框架本身"。**

---

## 三、边界在哪:范围可以长,值不能变

这是判断"什么能改"的唯一标准:

| | 范围(库) | 值(判定) |
|---|---|---|
| 是什么 | 有哪些检查项、字段、维度 | 本次任务里每条检查的判定结果 |
| 例子 | "evidence.result 字段"、"result=? 不算证据"这条规则 | 这次跑 mediainfo 得到 `6` |
| **能不能自迭代** | ✅ **可以**(受限地) | ❌ **绝对不行** |
| 为什么 | 它错了,下次同类问题会被发现 | 它错了,**这次就已经错了,而且没人知道** |

### 两条判据(两个都满足才允许自迭代)

| 判据 | 允许 | 禁止 |
|---|---|---|
| **它错了会传播到下游吗?** | 不会(只影响这一次的流程) | **会**(下游拿它当事实用) |
| **它错了会被自动发现吗?** | **会**(下次遇到同类问题就暴露) | 不会(要等到真出事) |

套用本项目:

| 候选 | 传播? | 会自动暴露? | 结论 |
|---|---|---|---|
| **检查项库**("这类问题该跑哪条命令") | 不传播 | **会** | ✅ 适合自迭代 |
| **`xcheck` 的维度清单** | 不传播 | **会** | ✅ 适合自迭代 |
| **规则筛本身的代码** | **会** | 不会 | ❌ 必须人来改 |
| **核心字段集** | **会**(改了历史记录不可比) | 不会 | ❌ 人 |

## 四、三条不对称(写进账本类型的硬约束)

| # | 不对称 | 为什么 |
|---|---|---|
| **1** | **只许"新增",不许"修改/删除"** | 风险不对称:新增一条规则最坏是漏检;**修改/删除一条规则,最坏是让之前所有依赖它的检查失效** |
| **2** | **只出"提案",不出"变更"** | AI 产出的是 change-request,采纳权在人。`needs` 永远是"人拍板" |
| **3** | **每次迭代必须留下触发证据** | `evidence` 必须指向**当时那个真实的失败案例**,不能指向"我觉得应该这样" |

第 3 条是复用消息总线已有的原则:**消息不许定义规则,只能指向规则**。
改 spec 同理:**不许凭空改,必须指向那个逼你改的事实。**

---

## 五、什么时候该记一条 `spec-gap`

**该记**(三条命中任意一条):

| 触发 | 例子 |
|---|---|
| **规则没覆盖**:你按规则做完了,但发现有一类情况没人管 | "收工自测"没覆盖"反查收件箱" |
| **规则写得笼统**:一个词可以指两件事,你差点理解成较轻的那件 | "自测"被理解成"跑测试" |
| **反复撞同一个坑**:同一类问题被问第二次 | "同一件事被问两次 = 系统缺陷" |

**不该记**(这些不是 spec-gap):

| 情况 | 该记成什么 |
|---|---|
| 我发现了一个 bug | `kind: task`,指给模块负责人 |
| 我需要别人做一个决定 | `kind: decision` |
| 我不知道该怎么做 | `kind: blocked`,说明卡在哪 |
| 规则写得很清楚,只是我不想遵守 | **什么都不记** —— 这是纪律问题,不是规则问题 |

> ⚠️ **最后一行是这套机制唯一可能被滥用的地方。**
> 如果一条"缺口"的理由是"这条规则让我多做了事",它就不是缺口。
> **判据:缺口是"规则没覆盖一类情况",不是"规则覆盖了我" 。**

## 六、字段说明

在 `PENDING.json` 的 `items` 里加一条,`kind` 填 `spec-gap`:

```jsonc
{
  "id": "specgap-简短标识",
  "title": "一句话说清哪条规则不够用(会被念出来,写人话)",
  "to": ["必须是人:规则的所有者(通常是发起人)"],
  "kind": "spec-gap",

  "hit_at": "2026-10-13T20:00:00Z",        // 必填:你**撞到**它的时刻(UTC,ISO8601)
  "source": "docs/ai-logs/ops/xxx.md#第10节", // 必填:证据出处(权威文档或日志锚点)

  "current_spec": "AGENTS.md 三、固定动作 第 5 步:自测",   // 必填:现行规则**原文位置**
  "proposed": "拆成三件互不替代的检查:①验证代码 ②验证输出 ③反查收件箱", // 必填:你建议怎么改

  "trigger": "收工两小时后别人提了新需求,PR 交上去才知道",  // 必填:触发它的真实事件
  "evidence": "我按规则①跑了测试全绿,但确实漏了新需求",     // 必填:可核对的证据

  "change_kind": "add",                    // 必填:add(新增) | modify(改) | remove(删)
  "adds": ["第 5 步增加第三项:反查收件箱"],   // change_kind=add 时必填
  "modifies": [],                          // change_kind=modify 时必填(列出被改条款)
  "removes": [],                           // change_kind=remove 时必填(列出被删条款)

  "needs": "人拍板",                        // 必填,且**只能是**"人拍板"
  "status": "pending-human",               // 必填:pending-human | adopted | rejected
  "action": "请确认这条缺口是否成立;成立则采纳为规范条款",  // 必填
  "note": "可选补充"
}
```

### 字段为什么要区分得这么细

| 字段 | 少了它会怎样 |
|---|---|
| `hit_at` | 无法判断这条缺口是不是在**本轮**撞到的(收工第 3 项要用) |
| `current_spec` | 人不知道你在说哪一条规则,只能猜 |
| `trigger` + `evidence` | 变成"我觉得应该这样",退化成意见 |
| `change_kind` + `adds/modifies/removes` | 无法机械执行"只许新增"这条不对称 |

## 七、谁来处理它

**收件人必须是人**(规则的所有者),AI 不能自行采纳。人的三个动作:

| 动作 | 操作 |
|---|---|
| **采纳** | 改权威文档 → 把 `status` 改 `adopted` → 在 ops 日志记一笔(哪条规则、谁改的、何时改的) |
| **驳回** | 把 `status` 改 `rejected`,**并写明理由** —— 否则同一个缺口还会被提第二次 |
| **搁置** | 保留 `pending-human`,但补 `note` 说明为什么不现在处理 |

> **驳回必须写理由**:本项目的原则是"同一件事被问两次 = 系统缺陷"。
> 驳回不写理由,下一个 AI 会重新提一遍,而它没有错。

---

## 八、机制自检:它自己也可能是错的设计

这套东西同样会撞到"规则不够用"。所以它自己也接受同一套待遇:

- 如果 `spec-gap` **没有被任何人处理过** → 说明规则的所有者不看收件箱,机制失效
- 如果 `spec-gap` **提交得太频繁**(比如每个任务都提) → 说明判据太松,或者规则真的差
- 如果 `spec-gap` **被驳回的比例很高** → 说明 AI 把"我不想遵守"误当成了缺口

**这三种情况都该记一条 `spec-gap` —— 关于这套机制本身。**
（即:本机制允许自我改进的提案,但不允许自我改进的实施。）

---

## 九、和其他条目的关系

| 条目类型 | 谁处理 | 能不能自动 |
|---|---|---|
| `task` | AI 可直接开工 | ✅ |
| `review` | 评审人 | ✅ |
| `must-know` | 知悉即可 | ✅ |
| `blocked` | 需要配合的人 | ⚠️ |
| `decision` | 人拍板 | ❌ |
| **`spec-gap`** | **人拍板(必须是规则所有者)** | ❌ **永远** |

**它和 `decision` 的区别**:`decision` 是"就这件事做个选择",**一次性**;
`spec-gap` 是"规则该改了",**会改变以后所有同类事情的做法**。

---

## 十、一句话总结

> **缺口由撞到它的人记录,由拥有规则的人裁决。**
>
> **AI 可以说"这条规则不够用",但不能说"所以我把规则改了"。**
