# 协作消息总线(Coordination Hub)

> **这套东西解决一个问题:需求变更以后,怎么让"别人和他的 AI"自己知道,而不是靠发起人一个个转述。**

---

## 一、为什么需要它(问题定义)

我们最初的协作方式是这样的:

```
发起人的 AI → 发起人(人) → 转述给其他使用者(人) → 他们的 AI
                    ↑                              ↓
             需求的"授权"在这里            对方 AI 认为:这不是我主人的要求
```

它有两个**结构性**断点,不是"沟通不积极"能解释的:

| 断点 | 原因 | 后果 |
|---|---|---|
| **授权断点** | 每个 AI 的工作依据是"**我主人要我做什么**"。转述过去的需求是"别人的话",不是主人指令 | 对方 AI 不主动推进 |
| **上报断点** | AI 只在**被唤起时**运行,**没有空闲时主动推送消息的能力** | 需求变了,对方主人不会知道 → 只能去问发起人 |

于是发起人变成了 API:**所有需求变更都要经过他转述一遍。**

---

## 二、解法:让需求住进仓库,并强制 AI 每轮开工先"念给主人听"

```
需求变更 → 写进仓库(权威) → 对方 AI 开工第一步读到 → 口述主人 → 主人拍板
                                    ↑
                        不需要发起人转述,也不需要对方来问
```

**四条设计原则**(后面所有规则都从这四条推出):

1. **仓库是唯一权威。** 需求变更的第一步永远是"改仓库文档",不是"发消息"。
2. **消息只负责送达,不负责定义规则。** 只出现在消息里、没进文档的要求,**视为不存在**。
3. **收件箱是推导物,不是真相源。** 所有 `INBOX-*.md` 由脚本生成,**禁止手工编辑**。
4. **默认被动,不默认主动。** 不依赖"AI 会主动推消息"(它做不到),只依赖"**AI 开工时一定会读**"。

---

## 三、这套东西由什么组成

| 文件 | 是什么 | 谁维护 |
|---|---|---|
| **`PROMPT-TO-AI.md`** | **给协作者的提示词模板**(复制粘贴即可):开工 / 收工 / 卡住三种场景,以及"AI 跑偏了长什么样" | 机制变更时更新 |
| **`PENDING.json`** | **唯一的待办账本**(结构化)。所有待办只有这一份 | 人 / AI 都可以加,但**只能改自己相关的条目** |
| `INBOX-<登录名>.md` | 每个人的收件箱(内含可直接转给使用者的提示词) | ⚠️ **脚本生成,禁止手改** |
| `STATUS.md` | 全局总览(谁有几条待办) | ⚠️ 同上 |
| `scripts/sync-inbox.mjs` | 生成器 + 一致性检查 | 改动机制时更新 |

### 先看这个:提示词

机制再好,**AI 不会自己去读收件箱** —— 除非使用者在开局把提示词贴给它。
所以每个协作者开工前应把 [`PROMPT-TO-AI.md`](PROMPT-TO-AI.md) 里的【开工提示词】复制给自己的 AI。
(每份 `INBOX-*.md` 底部也内嵌了一份精简版,AI 读完会主动把它转给使用者。)

生成/检查命令:

```bash
pnpm sync:inbox          # 重新生成三份收件箱
pnpm sync:inbox:check    # 只做一致性检查(来源文件是否存在、字段是否齐全)
```

## 四、怎么用(三种角色的动作)

### 发起人 / 任何提需求的人

1. **先改权威文档**(`CONTRACTS.md` / `ROADMAP.md` / `PROJECT_GUIDE.md` …)
2. **同一次提交里**在 `PENDING.json` 加一条,`source` 指向刚改的那份文档
3. 跑一次 `pnpm sync:inbox`,提交生成物

> ⚠️ **不要把协作需求只发在微信里** —— 那等于没发(见"通道边界")。

### 每个协作者(人)

开工时,你的 AI 会**把收件箱念给你听**。你要做的只有:确认他念的和你要的一致,然后拍板。

### 每个 AI

**开工第一件事**(写进 `AGENTS.md` 第 0 步,不可跳过):

1. 读 `docs/coordination/INBOX-<你的登录名>.md`
2. **把内容完整口述给你的使用者**(逐条念,带出处链接)
3. 等他确认后再开始干活

**完工时**(三件事,别混为一谈):

| # | 验证什么 | 怎么做 |
|---|---|---|
| ① | **代码** | `pnpm -r typecheck && pnpm --filter @fcp/api test` |
| ② | **输出** | 把这一轮**产生的需求**写进 `PENDING.json`;做完的条目删掉;跑 `pnpm sync:inbox` |
| ③ | **反查收件箱** | **重新读一遍自己的收件箱**,找出**开始时间晚于本轮开工时间**的条目 |

### 为什么 ③ 必须单独列一条(2026-10-13 补)

**问题**:AI 只在开工时读了一次收件箱。如果它这轮干了两小时,期间别人提了新需求,
**它不会知道** —— 于是 PR 可能"刚交上去就要返工",而且它是**在不知情的情况下**做错的。

**①②③ 的区别**:

- ① 证明**你的代码没坏**;
- ② 证明**你留下的信息能被别人读到**;
- ③ 证明**你干活期间世界变了、而你知道**。三者互不替代。

**判定方法(可执行)**:重读收件箱后,看每条待办的 `since` 是否**晚于你这轮开工的时间**。
是 → 那是"你干活期间新来的",必须念给使用者听并判断要不要返工。

**已知边界**:③ **不是实时**的。如果两个人几乎同时收工,可能互相看不到对方刚加的那条。
这种情况下,它会在**下一轮开工**时被发现 —— 属于**延迟**而非**丢失**,可以接受。

## 五、通道边界(能做什么,做不到什么)

| 通道 | 能否自动 | 说明 |
|---|---|---|
| Issue / PR 里 `@某人` | ✅ | 已验证可达,对方收到邮件 |
| 给 Issue 加 **assignee(指派)** | ✅ | 已实测 201 成功,**这是最可靠的定向触达方式** |
| 请求 review | ✅ | 对方收到评审请求通知 |
| 站内通知收件箱 `GET /notifications` | ✅ | 可读可管 |
| **私信某人** | ❌ | **GitHub 没有私信 API** |
| 微信 / 短信 / 机器人推送 | ❌ | 需要另建常驻服务器;本机不常驻,暂不做 |

**结论**:凡是要人拍板的事,都走 **GitHub Issue/PR + @ + 指派**,靠邮件触达。仓库里的收件箱负责"内容正确",GitHub 负责"提醒到位",两者分工。

## 六、防失控(必须遵守)

| 风险 | 规则 |
|---|---|
| **AI 互相 @ 刷屏** | **禁止只回复"收到/好的"**。任何评论必须携带**具体动作请求**或**状态更新**,否则视为噪声,评审可打回 |
| **消息变成事实规则** | 消息里**不得定义新规则**;发现"只在评论里说过、文档里没有"的要求 → 按**不存在**处理,并要求补文档 |
| **收件箱过时,反而误导** | 收件箱是生成物;`--check` 会校验每条 `source` 指向的文件是否存在 |
| **`PENDING.json` 被两人同时改** | 它属于**共享文件串行清单**;每人只动自己相关条目;冲突时**保留双方条目**(与 `INDEX.md` 同一处理原则) |
| **重复提问** | **同一问题被问第二遍 = 本系统的缺陷**,不是沟通问题。立刻把缺的条目补进 `PENDING.json`,并在该条 `note` 里写明"因被重复提问而补录" |
| **有人根本不看仓库** | 这不是系统能解决的:兜底是 GitHub 指派 + 邮件;仍不看 ⇒ **是人的问题**,不要再优化系统 |

## 七、它治不了什么(边界,别指望错)

| 治不了 | 原因 |
|---|---|
| "我同意这个变更"这类**拍板** | 决定必须由人做;系统只负责把"需要你拍板的事"送到他眼前 |
| 需要**改 `main`** 的收口 | 只有仓库所有者的令牌能写 `main`,最后一公里仍要人 |
| **完全离线**的人 | 仓库里的东西他永远不看 |
| 需要**新服务器**的推送(微信/短信) | 家庭项目不值当;真有需要再单独立项 |

---

## 八、失败排查(坏了怎么办)

| 症状 | 先查什么 |
|---|---|
| 对方说"我不知道要做这个" | 该条在 `PENDING.json` 里吗?`to` 写的是他的**登录名**吗(不是显示名)? |
| 收件箱内容不对 | 是不是有人手改了生成物?跑 `pnpm sync:inbox` 重新生成 |
| `--check` 报"来源不存在" | 你改文档时把 `source` 指向的文件改名/删了;修正 `source` |
| 同一件事被问第二次 | **系统缺陷**:补条目并在此文件里记一笔(这正是本机制的自我修正路径) |
| 收件箱里全是历史堆积 | 做完的条目没删;删掉,并在 ops 日志留痕 |

---

## 九、为什么不用别的方案

| 方案 | 为什么不用 |
|---|---|
| 建独立消息库 / 看板服务 | **第二个真相源** —— 本项目已经因为"同一规则两处写法"出过事故(F6)。真相源只能有一个 |
| 让 AI 空闲时主动推送 | **技术上做不到**:AI 不被唤起就不运行。任何依赖它的设计都会失败 |
| 微信机器人 / 短信 | 需要常驻服务 + 额外费用,收益不抵成本 |
| 把需求写在 Issue 里当唯一来源 | Issue 会被关、会被埋、不参与版本控制;规则必须能 `diff`、能追溯到 sha |
