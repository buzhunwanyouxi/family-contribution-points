# 给协作者用的提示词(复制粘贴)

> **怎么用**:把下面【开工提示词】整段复制给你自己的 AI 对话框。
> 它是这套协作机制的**入口** —— AI 读了它,才会去读收件箱、才会把变更念给你听。
>
> **为什么需要它**:AI 只会按你给的指令做事。你不说"先读收件箱",它就直接开始写代码了 ——
> 那么"需求变更自动送达"这件事就不会发生,你又得去问发起人。

---

## 一、开工提示词(每次开始干活时用)

> 只需改**第一行**的登录名,其余原样复制。

````text
我的 GitHub 登录名是 <你的登录名>,请在 family-points 仓库里按项目规则工作。

严格按以下顺序做,先不要写任何代码:

第 1 步 · 读收件箱
读 docs/coordination/INBOX-<你的登录名>.md(没有就运行 pnpm sync:inbox)。
把里面的每一条**完整念给我听**,逐条带上"权威出处"链接,不要总结成一句话。

第 2 步 · 补齐视野(只读,不要改)
读 AGENTS.md、docs/CONTRACTS.md、docs/ai-logs/OWNERS.md,
以及 docs/ai-logs/ops/ 里最近三篇日志。
然后回答我三件事:
  a) 有哪些模块没人占用、可以认领?
  b) 我打算做的这件事,依赖的接口定稿了吗?谁负责?
  c) 有没有别人刚踩过、我需要避开的坑?

第 3 步 · 写工作计划并**停下来等我确认**
按 AGENTS.md 第四节那张表填好(任务编号 / 目标模块 / 关联需求编号 / 本轮只改哪些文件),
再用一句话说明"做完之后,我怎么验证它是好的"。
**在我回复"开始"之前,不要动任何文件。**

第 4 步 · 干活(我确认后)
一次只做一个模块;**如果要认领模块,先把 OWNERS.md 的认领改动单独提交一次,再开始写代码** ——
否则两个人可能同时认领同一个模块,白干一场(认领的"提交"才是真正的锁);
改了共享文件(见 CONTRIBUTING.md 第 5 节)要在日志里说明;
不碰别人声明为"进行中"的模块。

第 5 步 · 收工,按顺序做完这八件(缺一件都算没做完)
  ⚠️ 不要用"跑测试"代替 ⑤ ⑥ ⑦ 三件 —— 它们验的是不同的东西。

  ① 自测代码:pnpm -r typecheck && pnpm --filter @fcp/api test,把原始输出贴给我
  ② 写 ops 日志与 report(模板在 docs/ai-logs/README.md,第 7、8 节必填)
  ③ 更新 INDEX.md、以及你改过的契约行;并更新 OWNERS.md 的进度
     (改了哪个模块,就改那一行的状态 / 最后更新 / 实测进度 —— 不更新的话下一个人会照过期表安排工作)
  ④ 留下你产生的需求:该别人做的事写进 docs/coordination/PENDING.json,
     跑 pnpm sync:inbox,并把生成物一起提交 —— 见下面【留需求的写法】
  ⑤ **反查收件箱(别人在我干活期间给我加了什么)**:
     - 重新读一次 docs/coordination/INBOX-<你的登录名>.md
     - 找出**开始时间晚于我这轮开工时间**的条目
     - 逐条念给我听,并说明:会不会影响我刚写完的东西?需不需要返工?有没有变成阻塞?
     - 如果有一条让你"差点做错",把它写进你的 ops 日志第 8 节
  ⑥ **检查解锁(我给别人解除了什么)**:这一条是 ⑤ 的反方向,不能省。
     - 看收件箱里的「**谁在等你**」一节 —— 那些待办卡在你这里
     - 你这轮做完的事,有没有解除其中某条的 waiting_on?
     - 有 → 去 PENDING.json 把该条的 `waiting_on` 删掉,**否则对方不知道已经解锁**
       (对方只会重读自己的收件箱,而"解锁"表现为别人删了一条,他是看不见的)
  ⑦ **记录规则缺口(必填,没有就写"无")**:
     - 这一轮**有没有撞到"规则不够用"**?比如:规则没覆盖某类情况、某个词你差点理解成较轻的那件、
       同一类坑被问第二次
     - 有 → 按 [`SPEC-GAP.md`](SPEC-GAP.md) 提一条 `kind: spec-gap`(在 `PENDING.json` 里)
     - **红线**:不许绕过规则,更**不许自己改规则**(AGENTS.md 禁令 8)。
       被约束者不得修改约束 —— 否则"这条检查太麻烦"就成了合法的修改理由
     - **判据**:缺口是"**规则没覆盖一类情况**",不是"**规则覆盖了我**"。
       如果理由只是"这条规则让我多做了事",**什么都不要记** —— 那是纪律问题
  ⑧ 提 PR,并在 PR 里明确写:"我已自测通过,请求评审 @buzhunwanyouxi" + 我该点哪里验证

过程中如果卡住:**不要猜**。把完整报错、你已经试过什么、你判断需要谁介入写进日志,然后告诉我。
````

## 二、留需求的写法(第 5 步第 4 项展开)

**不要**在微信里说"这个让 B 去做" —— 那等于没说。
**要**把它写进账本,让对方自己的 AI 下次开工时念给他的主人听。

在 `docs/coordination/PENDING.json` 的 `items` 里加一条:

```jsonc
{
  "id": "简短唯一的英文标识",
  "title": "一句话说清要做什么(会被念出来,写人话)",
  "to": ["对方的 GitHub 登录名"],          // 必填,登录名不是显示名
  "kind": "task",                           // task | decision | review | blocked | must-know
  "since": "变更发生的时间(UTC,ISO8601)",   // 不是你现在写这条的时间
  "source": "docs/CONTRACTS.md#接口编号",    // 必填:权威出处。没有出处 = 这条要求不成立
  "action": "对方具体要做什么(可执行的一句话)",
  "needs": "AI 可直接开工",                  // 或 "人拍板"
  "waiting_on": ["要等的登录名或事件"]        // 可选但强烈建议,见下
}
```

### 关于 `waiting_on`:它是"解锁信号"的唯一载体

**没有它就会丢信号**:假设你的待办写着"等 B 的 PR 合并后我才能开工"。
B 做完之后,**他能做的事是"删掉自己那条待办"** —— 而不是给你加一条。
于是你重读自己的收件箱时,**什么新条目都看不到**,却已经被解锁了。

所以:

- **等待方**写 `waiting_on: ["MIAO98J"]` —— 这样你会在自己的收件箱里看到"要等:MIAO98J";
- **被等的人**收工时看收件箱的「**谁在等你**」一节 —— 那里列着所有卡在他身上的待办;
- **做完的人负责把 `waiting_on` 删掉**(或直接删掉整条),这就是解锁信号。

**收尾检查因此是两个反方向的动作**:
⑤ 看"别人给我加了什么"(新增条目);⑥ 看"我给别人解除了什么"(`waiting_on` 消失)。**缺一个都会漏。**

然后:

```bash
pnpm sync:inbox          # 重新生成收件箱
pnpm sync:inbox:check    # 校验:kind 合法吗?source 指向的文件存在吗?
```

把 `PENDING.json` 和 `INBOX-*.md` 一起提交。

**三条硬规矩**(`CONTRIBUTING.md` 第 5.1 节):

1. 只回"收到/好的"**不算沟通**,评论必须带具体动作请求或状态更新;
2. **消息里不得定义新规则** —— 只出现在消息里、没进文档的要求,按"不存在"处理;
3. **同一件事被问第二次 = 系统缺陷** —— 补录进账本,而不是再解释一遍。

## 三、收工提示词(阶段性收尾时用)

````text
请做收工检查,逐项回答,不要略过:

【验证代码】
1. 你这一轮改了哪些文件?和开工时计划的名单一致吗?不一致的地方为什么?
2. pnpm -r typecheck 和 pnpm --filter @fcp/api test 的结果是什么?把原始输出贴出来。

【验证输出】
3. ops 日志里第 7 节(给下一个接手者的交接建议)写了什么?念给我听。
   第 8 节(在别人代码里发现的问题)写了吗?没有就写"无"。
4. 你这轮产生了哪些**别人需要知道的需求**?
   把它们写进 docs/coordination/PENDING.json,跑 pnpm sync:inbox,把生成物提交。
   然后**把每条念给我听** —— 我要确认有没有写错人。

【反查收件箱 —— 这一条最容易漏,它和上面的"自测"是两件不同的事】
5. 现在重新读一遍 docs/coordination/INBOX-<我的登录名>.md,然后回答:
   a) 里面有没有**开始时间晚于我这轮开工时间**的条目?
      (也就是:别人**在我干活期间**新提出来的需求)
   b) 如果有,逐条念给我听,并判断:会不会影响我刚写完的东西?需不需要返工?
   c) 有没有哪一条让你"差点做错"?那要写进你的 ops 日志第 8 节。
   d) 有没有哪一条其实已经被你顺带解决了?如果有,把它从 PENDING.json 移除。

【检查解锁 —— 这是第 5 条的**反方向**,不能省】
6. 看同一份收件箱里的「**谁在等你**」一节,然后回答:
   a) 有哪些待办**卡在我这里**?
   b) 我这轮做完的事,解除了其中哪几条?
   c) 对已解除的,**去 PENDING.json 把对应的 `waiting_on` 删掉**(或删掉整条)——
      否则对方不知道已经解锁,他会一直等下去。
   d) 如果某条你还没做完,那就**什么也不要删**,让对方继续等。

【记录规则缺口 —— 必填,没有就写"无"】
7. 这一轮**有没有撞到"规则不够用"**?逐条自问:
   a) 有没有"规则没覆盖"的一类情况?(我按规则做完了,但发现有一类情况没人管)
   b) 有没有哪个词**差点被我理解成较轻的那件**?(例:"自测"被理解成"跑测试")
   c) 有没有同一类坑**被问第二次**?
   有 → 按 `docs/coordination/SPEC-GAP.md` 在 PENDING.json 里提一条 `kind: spec-gap`;
   没有 → **写"无"**。
   ⚠️ **不许绕过规则,更不许自己改规则**(禁令 8)。判据:**缺口是"规则没覆盖一类情况",
   不是"规则覆盖了我"** —— 如果理由只是"这条规则让我多做了事",什么都不要记。

【收尾】
8. 有没有你做完之后、别人才能接着做的事?如果有,那也要写进 PENDING.json,to 填对方。
9. PR 提了吗?PR 描述里有没有写"已自测通过,请求评审"?我该点哪里做人工验证?
```

> **为什么第 5、6 条要单独问**:AI 开工时读过一次收件箱,但**那之后别人可能又提了新需求**(第 5 条),
> 也可能**别人在等你、而你做完了却没告诉他**(第 6 条)。
> 这两件事方向相反,只做一件都会漏 —— 前者让你返工,后者让别人白等。

## 四、卡住时的提示词(不猜、不乱改)

````text
停一下,不要继续尝试修复,也不要改动任何文件。

请你:
1. 用一句话说清现在卡在哪;
2. 贴出**完整的**报错信息(不要只贴最后一行);
3. 列出你已经试过的办法,以及每一次的结果;
4. 判断这是"我能自己解决"还是"需要人介入";如果是后者,说清需要谁做什么;
5. 把上面这些写进你的 ops 日志(卡住也必须写日志 —— AGENTS.md 禁令 7)。

写完告诉我,我们一起决定下一步。
````

## 五、给 AI 的补充说明(不用复制,供你判断它有没有跑偏)

| 现象 | 说明它跑偏了 |
|---|---|
| 它直接开始写代码,没念收件箱 | 第 1 步没做 —— 这是本机制**唯一**的依赖点,请打断它 |
| 它把收件箱"总结成一句话" | 不行,必须逐条念。总结会丢掉出处,你就无法自己去核对 |
| 它改了 `INBOX-*.md` | 那是生成物,改了下次会被覆盖。要改就改 `PENDING.json` |
| 它说"我顺便也把别人的模块改了" | 违反 AGENTS.md 禁令 5,让它回退 |
| 它说"这个我猜是这样实现" | 违反禁令 1。规则只能来自文档,文档没写清就走"日志 → Issue → 改文档" |
| 它做完没说"请求评审" | PR 流程没走完,见 CONTRIBUTING 第 4.1 节 |

## 六、这套提示词和"人肉中转"的关系(一句话)

**以前的链路**:发起人 → 你 → 你的 AI(它不知道需求变过)。
**现在的链路**:仓库 → **你的 AI 主动念给你听** → 你拍板。
这两条链路的差别,就在于你开局有没有把【开工提示词】贴给它。
